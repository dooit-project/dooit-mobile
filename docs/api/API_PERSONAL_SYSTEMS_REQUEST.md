# 시스템·실천 증거 기능 백엔드 개발 요청서

작성일: 2026-10-12

전달 상태: 2026-10-12 사용자 확인으로 백엔드 담당자에게 전달 완료. 회신·계약 합의·구현·배포는 미확인.

상태: 신규 개발 요청 초안. 백엔드 구현·배포·API 합의는 확인하지 않았다. 이 문서 전체를 백엔드 담당자에게 복사해 전달할 수 있다. 백엔드 구현과 DB 변경은 별도 `dooit-backend` 저장소에서 진행한다.

## 요청 목적과 범위

Dooit에 “원하는 방향 → 시스템 하나 → 오늘 실천 → 일주일의 증거 → 시스템 조정” 흐름을 추가하려고 합니다. 목표 날짜를 필수로 하지 않으며 시작 조건·기본 행동·최소 행동을 중심으로 실행합니다. 최소 행동도 유효한 실천이며, 휴식과 기록 없음은 실패로 분류하지 않습니다.

첫 버전은 개인 시스템 하나 중심입니다. 복수 시스템 관리·Workspace·점수·연속 달성·타이머·자동 일정 재배치·서버 push·문구 CMS는 제외합니다. 기존 반복 Task·완료·알림 계약의 재사용 가능 여부부터 확인해 주세요. 기존 Daily Plan·summary·체크리스트를 신규로 다시 개발해 달라는 요청은 아닙니다.

## BE-01. 시스템 저장·관리

사용자별 시스템 생성·목록/상세 조회·수정·일시정지·재개·종료가 필요합니다.

최소 필드 제안:

- `id`, 소유 사용자, `version`, 생성·수정 시각
- `directionText`: 기한 없는 바람, `motivationText`: 선택적인 이유
- `triggerText`: “저녁 식사 후” 같은 시작 상황
- `schedule`: 반복 요일·기준 시작일·IANA 시간대, 선택적 알림 시각
- `standardAction`, `minimumAction`: 행동 설명과 선택적인 목표 분량/예상 시간
- `nextAction`: 다음 실행의 첫 행동
- `status`: ACTIVE / PAUSED / ARCHIVED 제안
- 선택적인 D-Day 연결, 반복 Task 연결 식별자

시스템이 바뀌어도 과거 실행 당시의 행동·주기·최소 행동을 확인하도록 버전 또는 회차 스냅샷을 보존해 주세요. 기존 Task 제목 30자·설명 300자 및 예상 시간 5~1440분 제약을 새 데이터에 그대로 적용하지 말고 각 필드 길이·단위·범위를 합의해 주세요. 1분 행동이나 시간 없는 행동도 표현할 수 있어야 합니다.

## BE-02. 실행 회차·Task 연결

- 사용자 시간대와 주기에 따라 예정 회차를 생성/조회하고 중복을 막아 주세요.
- 회차마다 고유 ID, 시스템 ID·버전, 예정 서비스 날짜, 연결 Task 식별자를 제공해 주세요.
- “식사 후” 상황은 텍스트 조건이며 자동 감지하지 않습니다. 알림 시각은 별도입니다.
- 시스템 수정은 선택한 적용 시점 이후 회차에 적용하고 과거 기록은 보존해 주세요.
- 지난 미실행 회차가 Today·오래 미룬 일에 자동 누적되지 않아야 합니다. 단순 조회로 과거 회차 상태를 변경하지 말아 주세요.
- 이번 회차 쉬기와 시스템 전체 일시정지를 구분하고 재개 시 누락 회차를 몰아서 만들지 말아 주세요.
- 한 회차당 유효한 실천 결과 하나를 기본으로 합니다. 추가 실천을 받는 기능은 첫 버전에서 제외합니다.
- 시스템의 다음 행동을 수정하는 것과 진행 중인 회차의 표시 내용을 갱신하는 범위를 명확히 해 주세요.

기존 반복 Task occurrence를 확장할지 별도 회차를 연결할지 설계안을 회신해 주세요. 현재 반복의 미루기·건너뛰기·수정 범위 및 D-Day 연결과 충돌하지 않아야 합니다.

## BE-03. 실천·휴식·메모 기록

회차 상태는 PENDING / PRACTICED / RESTED를 제안합니다. 지난 PENDING은 “기록 없음”으로 표현하며 실패·휴식으로 자동 바꾸지 않습니다.

실천 시 필요한 데이터:

- `actionVariant`: STANDARD / MINIMUM
- 실제 사용자가 확인한 실천 시각(시간대 해석 규칙 포함)
- 선택적인 `accomplishedNote`, `nextAction`
- 선택적인 어려움: 시간 없음 / 첫 행동 불명확 / 버거움 / 잊음 / 기타
- 갱신 버전 또는 동등한 충돌 검출 정보

시작하기 선택은 실천 완료가 아닙니다. 선택한 예상 시간이 실제 소요 시간이 되지 않도록 해 주세요. 최소 행동도 회차 실천 완료로 인정하지만 프로젝트 전체 완료를 뜻하지 않습니다.

실천 저장·수정·취소, 휴식 선택·취소가 필요합니다. 연결 Task의 완료/재개와 실행 기록이 원자적으로 일치하도록 해 주세요. 기존 Task 목록에서 직접 체크할 때 기본/최소를 알 수 없다면 UNKNOWN 같은 명시적 값을 허용하거나 추가 확인 계약을 합의해야 합니다. 기본 행동을 했다고 추정하면 안 됩니다.

다음 행동을 입력하지 않은 경우 유지, 명시적 비우기, 새 값 저장을 구분해 주세요. 과거 기록 수정으로 더 최근에 저장한 다음 행동을 덮어쓰지 않도록 규칙이 필요합니다.

## BE-04. 주간 증거 조회

시스템 ID·기간·시간대에 따른 조회가 필요합니다.

- 조회 범위와 집계 기준 시간대, 일자별 원본 실행 기록
- 실천 회차 수와 실천 날짜 수를 별도 제공
- 기본·최소·종류 미확인 실천 수, 사용자 선택 휴식 수
- 기록 없음과 기록 조회 실패 구분
- 메모, 해당 시스템 버전/스냅샷, 원본 실행 ID
- 기록 수정·취소 이후 집계 일치와 요약 버전 갱신

완료 비율·점수·연속 달성은 요청하지 않습니다. 첫 화면의 주간 범위를 최근 7일로 할지 달력 주간으로 할지는 제품 검토에서 확정하므로 명시적 시작일·종료일 조회를 지원해 주세요. 날짜 경계 포함 규칙과 기간 상한도 명시해 주세요.

## BE-05. AI 초안·회고·조정

1. 바람·사용자가 제공한 일상 조건을 받아 시스템 하나의 구조화된 초안을 반환합니다. 사용자 확정 전 저장·회차 생성은 하지 않습니다.
2. 확정된 집계·메모만으로 주간 요약을 생성합니다. 횟수·날짜는 서버 계산값을 사용하고 근거 실행 ID를 연결합니다. 기록에 없는 성과·감정·실제 시간을 만들지 않습니다. 근거가 없으면 생략하거나 정형 요약을 반환합니다.
3. 현재 시스템과 사용자가 고른 어려움으로 조정 초안을 반환합니다. 사용자 확인 전 자동 변경하지 않습니다. 조정 AI는 핵심 루프 이후 제공해도 됩니다.

AI 키는 서버에서 관리해 주세요. 구조화 응답 검증, 타임아웃, 사용자별 요청 제한, 안정적인 오류 코드와 재시도 정책이 필요합니다. 기록·시스템 변경 시 오래된 요약을 재사용하지 않도록 입력 버전으로 관리해 주세요. 실패해도 시스템 CRUD·실천·원본 조회는 가능해야 합니다.

바람·메모의 AI 전송 항목, 공급자와 보관·삭제 정책을 회신해 주세요. 개인정보가 포함될 수 있는 입력을 운영 로그에 그대로 남기지 않는 정책이 필요합니다.

## BE-06. 알림·다독임 콘텐츠

첫 버전은 기존 로컬 알림을 사용합니다. 회차별 안정적인 알림 식별자, 예정 시각, 취소/변경 판별 정보를 제공해 주세요. 휴식·일시정지·주기 변경 시 예약을 정리할 수 있어야 합니다. 서버 push 신규 구현은 요청하지 않습니다.

응원·명언은 앱 내 검토된 정적 콘텐츠와 로컬 노출 설정으로 시작합니다. 신규 서버 API는 필수가 아닙니다. 후속 CMS가 필요하면 문구 ID·본문·유형·노출 맥락·저자·출처·언어·사용 조건·활성 상태·버전을 관리합니다. 명언을 AI가 임의로 인물에게 귀속하는 기능은 요청하지 않습니다.

## 예상 API 형태 — 합의 전 제안

| 작업                     | 경로 제안                                                       |
| ------------------------ | --------------------------------------------------------------- |
| 시스템 생성·조회         | POST / GET `/api/v1/personal-systems`                           |
| 상세·수정·상태 변경      | GET / PATCH `/api/v1/personal-systems/{systemId}`               |
| 기간별 예정 회차         | GET `/api/v1/personal-system-occurrences?from=…&to=…`           |
| 회차 결과 저장·수정·취소 | PUT `/api/v1/personal-system-occurrences/{occurrenceId}/result` |
| 시스템 주간 증거         | GET `/api/v1/personal-systems/{systemId}/evidence?from=…&to=…`  |
| AI 시스템 초안           | POST `/api/v1/personal-systems/draft`                           |
| AI 조정 초안             | POST `/api/v1/personal-systems/{systemId}/adjustment-draft`     |
| AI 회고                  | POST `/api/v1/personal-systems/{systemId}/reflection`           |

이 경로는 현재 사용 가능한 API가 아닙니다. result 취소는 PENDING 상태 저장 등 하나의 명시적 계약으로 확정해 주세요. GET evidence는 AI 호출 없이 원본·집계를 반환하고, AI 회고 요청은 별도로 분리하는 것을 제안합니다.

## 공통 계약과 회신 요청

- 인증·개인 소유권 검증과 타 사용자 리소스 비노출. 게스트 지원·계정 연결/병합·로그아웃 이후 데이터 처리 범위.
- 생성은 기존 Idempotency-Key 정책에 맞는 중복 방지, 결과 저장 PUT은 자체 멱등성. 재시도·동시 요청·다른 payload 충돌 규칙.
- 시스템/회차 수정의 version 충돌 응답과 새로고침 후 재시도 방법.
- 시간대 변경·자정·DST·실천 시각과 예정일 불일치·과거 기록 입력 허용 범위.
- 활성 시스템 개수, 필드 길이·분량 단위, 조회 상한·pagination, 오류 코드·validation 응답.
- 알림 동기화와 Task 완료/재개·수정·삭제 시 시스템 기록 처리 정책. 시스템 종료는 과거 증거를 보존하는 것을 제안하며 영구 삭제는 첫 버전 범위 밖입니다.
- 확정 OpenAPI·요청/응답 예시·migration·테스트 결과·배포 식별 정보 및 검증 환경 제공.

## 수용 기준

- 같은 생성/실천 요청을 재시도·병렬 처리해도 시스템·회차·실천이 중복되지 않습니다.
- 최소 행동 실천이 정상 완료로 표시되고 실제 시간·성과를 추정하지 않습니다.
- Task 직접 완료·취소와 회차·주간 집계가 일치하고 미확인 행동 종류를 추정하지 않습니다.
- 휴식·일시정지·재개·주기 변경 후 과거 누락이 Today에 누적되지 않고 알림이 정리됩니다.
- 시스템 수정 후 과거 행동 스냅샷이 보존됩니다. 오래된 기기의 변경은 충돌을 검출합니다.
- 주간 회고는 원본으로 검증 가능하며 수정·취소 후 오래된 근거를 사용하지 않습니다.
- AI 장애에서도 직접 작성·실천·기록 조회가 됩니다. 다른 사용자 데이터 접근은 차단됩니다.

프론트에서는 합의된 계약으로 mock·API client·화면을 구현하고 Android·iOS·Web 검증을 진행합니다. 먼저 기존 기능 재사용 범위, 미결정 정책, 확정 DTO/OpenAPI와 구현 순서를 회신해 주세요.
