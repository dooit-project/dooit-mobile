[백엔드 회신 대조 기록](../integration/BACKEND_HANDOFF_2026-10-18.md)에 따라 새 Goal/복수 계획/회차 결과·휴식/일회성 Task·직접 기록/통합 여정의 계약·controller를 확인했습니다. image `6cdc9e5`에서 목표 schema와 인증 후 목표 API·여정 집계·owner 경계를 검증했다는 백엔드 보고를 수신했습니다. 이 문서의 G-01~05 전체를 아직 서버 미구현으로 취급하지 않습니다. 모바일 DTO/API/화면 연결·실제 개인 데이터 이관·Android 확인은 남아 있습니다.

새 `/api/v1/goals`와 기존 D-Day는 별도 모델이며 ID·Task 연결을 혼동하지 않습니다. 목표일 미정과 여러 계획은 새 모델을 사용합니다. 개인 시스템 이관은 명시적 API이고 실제 사용자의 이관은 미실행입니다. AI는 네 API 기반만 있고 기본 비활성 503/provider 정책 대기입니다.

**목표 색상과 G-06 서버 순서는 별도 미확인입니다.** 확인한 Goal 생성/수정/조회 DTO에 colorKey가 없고 이번 보고에 순서 저장 계약도 없습니다. 로컬 저장을 서버 동기화 완료로 바꾸거나 G-06 전달을 추정하지 않습니다. 아래 경로 제안은 요청 이력이며 실제 구현 경로는 회신 기록과 백엔드 계약을 따릅니다.

## 2026-10-18 추가 확인 — Web AI 사용 제한 헤더

로컬 API 오류 처리에서 429/70010의 `Retry-After` 반환을 확인했지만, 확인한 `CorsConfig.exposedHeaders`에는 Idempotency-Replayed만 있습니다. Web에서도 서버가 안내한 재요청 시각을 읽도록 `Retry-After` 노출을 확인·추가해 주세요. 모바일은 헤더가 없으면 시간 미상으로 처리하며 임의 카운트다운을 만들지 않습니다. 이 추가 요청은 아직 전달·합의·배포를 확인하지 않았습니다. 운영 CORS를 직접 호출한 결과는 아닙니다.

## 기존 요청에서 달라진 핵심

기존 [개인 시스템 요청서](./API_PERSONAL_SYSTEMS_REQUEST.md)는 이미 전달됐습니다. 사용자 요구를 구체화하면서 첫 버전의 중심을 **목표 하나 → 여러 반복 계획 + 일회성 행동 → 목표별 실천 여정**으로 수정합니다. 기존 요청의 개인 시스템 하나 제한·복수 시스템 제외를 이 변경 요청으로 대체합니다. 한 반복 회차의 유효 결과 하나라는 중복 방지 원칙은 유지하되 목표에 별도의 일회성 노력은 여러 개 추가할 수 있어야 합니다.

예: 토익 900점, 목표일 2026-11-30 → 매일 단어 30개 + 선택한 주말 요일 문제 5개 → 오늘 추가로 문제 30개 풀기 → 목표별로 실제 해온 과정을 조회. 날짜와 분량은 사용자 입력 예시입니다.

## G-01. 목표 모델·기존 D-Day 재사용

- 목표 이름, 선택적인 원하는 결과/이유, 선택 목표일, 상태(진행/일시정지/달성/보관 제안), 생성·수정/버전이 필요합니다. 날짜는 쉽게 입력하되 미정도 허용합니다.
- 목표를 Today와 계획 목록에서 구분할 수 있도록 사용자 선택 색상을 Goal에 저장해야 합니다. `colorKey`처럼 서버와 클라이언트가 합의한 안정적인 식별자를 생성·조회·수정 DTO에 포함하고 계정의 모든 기기에서 동기화해 주세요. 첫 후보는 `SAGE`, `BLUE`, `AMBER`, `CORAL`, `VIOLET`, `TEAL`이며 실제 hex 값은 앱 테마가 관리합니다.
- 기존 목표와 색상 미입력 요청은 서버 기본값 또는 `null`을 허용해 점진적으로 이전할 수 있어야 합니다. 지원하지 않는 색상 값은 명확한 4xx validation 오류를 반환하고, 목표 색상 변경이 기존 Task·실천 기록의 귀속이나 집계에는 영향을 주지 않아야 합니다.
- 날짜·설명 수정과 사용자 확인에 의한 달성 기록이 필요합니다. 기한 도래·행동 완료 수로 자동 달성/실패 처리하지 않습니다. 복잡한 지표 엔진은 요청하지 않습니다.
- 기존 D-Day의 필수 targetDate를 확장할지, 별도 Goal과 매핑할지 제안 부탁드립니다. 기존 목표 ID·Task 연결·날짜·알림/deep link·완료 기록을 보존해야 합니다.
- 목표 달성/보관 시 미래 계획을 멈출지 유지할지 명시적 정책과 선택이 필요합니다. 과거 실천은 보존합니다. 기존 복수 목표를 하나로 줄이거나 삭제하지 않습니다.

## G-02. 목표 아래 여러 반복 계획

- Goal 1:N 실행 계획, 실행 계획 1:N 회차를 지원합니다. 목표 없는 독립 반복 행동도 기존 사용 범위와 충돌하지 않게 유지합니다.
- 계획마다 이름·주기·기준일/시간대·선택 시작 시각/상황·선택 알림·기본/최소 행동·선택 다음 행동·상태/버전을 둡니다. 단어와 문제풀이를 각각 수정/정지/재개할 수 있어야 합니다.
- 시작 시각 없는 매일·선택 요일 반복을 지원하고, 일반 일정 startAt을 불필요하게 강제하지 않습니다. 기존 [일상 반복 확인 항목](./API_PERSONAL_SYSTEMS_DAILY_CLARIFICATION.md)의 시간/알림/요일/nextAction 정책도 함께 확인해 주세요.
- 목표와 반복 계획의 연결이 회차에도 반영되어야 합니다. 연결 변경은 미래에 적용하고 과거 귀속은 보존하는 것을 기본 제안으로 둡니다. 기존 완료 기록의 귀속 수정은 별도 명시적 행동으로 처리합니다.
- 주말 중 임의 1회와 토·일 각각은 다릅니다. 초기 날짜 기반 계획에서는 선택 요일별 회차를 지원합니다. 기간 내 N회 엔진을 이미 지원하는지 별도로 알려 주세요. 이번 요청만으로 신규 기간 목표 엔진 구현을 필수화하지 않습니다.

## G-03. 일회성 행동·이미 한 일 기록

- 목표 상세에서 일회성 Task 생성 시 목표가 자동 연결되고, 일반 Task 생성/상세에서도 목표를 선택·연결할 수 있어야 합니다. 기존 D-Day Task 생성/연결 API 재사용 가능 여부를 확인해 주세요.
- 계획하지 않았지만 이미 한 일은 실제 실천 날짜·행동 제목·선택 메모로 바로 기록할 수 있어야 합니다. 원자적인 완료 Task 생성 또는 독립 실행 기록 중 중복 방지·조회가 일관된 방식을 제안해 주세요.
- 추가 실천을 기존 반복 회차의 기본/최소 결과로 억지로 바꾸지 않습니다. 일회성 기록은 해당 계획의 주말 회차를 자동 완료하지 않습니다.
- 생성 중복 재시도와 완료 기록의 생성/수정/취소를 지원합니다. 기존 Task를 목표에 연결하는 경우 새 실천을 복제하지 않습니다.

## G-04. 목표의 지나온 길

- Goal ID·명시 기간·시간대·cursor 기반의 전체 여정 조회가 필요합니다. 주간뿐 아니라 목표 시작 이후도 조회합니다.
- 반복 회차 실천과 일회성 Task 완료/직접 기록을 통합하되 원본 종류·ID·실천 날짜·당시 목표/계획/행동·기본/최소/종류 미확인·메모를 제공해 주세요.
- 연결 Task와 반복 회차는 같은 원본으로 중복 집계되지 않아야 합니다. 계획 변경 이력·목표 결과는 보여줄 수 있되 실천 수에 넣지 않습니다.
- 목표별 실천 회차/일회성 완료 수·실천 날짜 수 등 집계는 전체 원본 기준으로 제공합니다. 페이지 일부를 전체로 간주하지 않습니다. 최소 행동·휴식·기록 없음은 기존 원칙대로 구분합니다.
- 계획한 분량에서 실제 학습량/시간을 계산하지 않습니다. 첫 버전은 분량 합계가 없어도 되며, 실제 분량을 받는다면 단위/실제 입력 여부가 분명해야 합니다. 점수 상승·목표 달성률 자동 추정은 요청하지 않습니다.
- 완료 취소·Task 변경·목표 연결 수정 후 원본과 집계·AI 요약이 일치해야 합니다. 과거 기록을 없애는 계획 재생성은 피합니다.

## G-05. 스스로 계획하고 AI는 보조

사용자가 직접 목표·반복 계획 여러 개를 만들 수 있어야 합니다. AI는 목표 구체화·행동 초안·조정과 실제 기록 요약을 보조하며 자동 확정하지 않습니다. 생성 장애에도 CRUD·실천·여정 조회는 동작해야 합니다. 개인 메모/목표의 AI 전달 범위·보관 정책은 기존 요청과 같습니다. 동기 문구 순환은 앱 로컬 기능으로 신규 서버 요청이 아닙니다.

## G-06. 목표와 계획 항목의 사용자 지정 순서 — 2026-10-16 추가, 미전달

- **목표 순서:** 계획의 가로 목표 탭과 전체 목표 목록은 같은 사용자 순서를 사용해야 합니다. 새 목표의 기본 위치, 삭제·보관·복원 시 위치 규칙을 명시해 주세요. 기본 제안은 새 목표를 뒤에 추가하고 기존 항목의 상대 순서를 보존하는 것입니다.
- **목표 안 항목 순서:** 반복 계획·일회성 할 일·일정을 종류별로 강제 분리하지 않고 하나의 목록에서 사용자가 섞어 배치할 수 있어야 합니다. 나중에 만든 시험 접수 일정을 반복 행동보다 위에 둘 수 있어야 합니다.
- 두 순서는 계정에 저장해 기기 간 동기화해야 합니다. 목표 색상처럼 별도 앱 로컬 설정이 최종 원본이 되는 기능이 아닙니다. 모바일은 계약 전 목표 순서와 목표별 표시 항목 순서를 계정/API 환경별 로컬에 임시 저장하며 서버 지원을 주장하지 않습니다. 항목의 임시 표시 키를 서버에 전송하거나 확정 엔터티 ID로 간주하지 않습니다.
- 순서 변경은 목표일·Task 날짜·반복 규칙·목표 소속·완료 기록을 바꾸지 않습니다. 달력 날짜순과 Today 실행 순서 API와도 분리합니다. Workspace의 순서 변경 요청이 아닙니다.
- 계획 목록에는 **안정적인 항목 ID와 원본 종류/ID**가 필요합니다. 반복 묶음은 매일의 Task ID 대신 반복 정의를 대표하는 항목 ID를 사용해야 합니다. 회차 예외의 별도 표시/순서 정책도 정해 주세요. 프론트에서 만든 `series:<id>:<rule>` 표시 키는 서버 엔터티 ID가 아니므로 API 계약으로 보내지 않습니다.
- 조회 응답에 저장 순서와 순서 버전(또는 동등한 동시 수정 제어)을 포함해 주세요. 전체 목록을 재정렬하는 요청은 같은 사용자의 현재 대상 목록인지 확인하고 중복·누락·다른 소유자의 ID를 거부해야 합니다. 동시 생성·삭제로 목록이 달라졌을 때의 재조회/재적용 규칙과 409 예시도 필요합니다.
- 정렬 적용은 원자적으로 처리해 일부 항목만 순서가 바뀌는 성공을 만들지 않습니다. 응답은 서버가 수락한 순서와 최신 버전을 반환해야 합니다. 저장 실패 시 기존 순서를 보존하고 같은 의도 재시도가 안전해야 합니다.

경로·필드명은 아래 **제안**이며 운영 API로 사용하지 않습니다. 기존 Goal 모델로 이행할 경우 동등 계약으로 회신해 주세요.

```text
GET /api/v1/dday-goals → goals, orderVersion
PUT /api/v1/dday-goals/order
  { orderedGoalIds: [12, 8, 21], expectedVersion: 3 }
GET /api/v1/dday-goals/{goalId}/plan-items → items, orderVersion
PUT /api/v1/dday-goals/{goalId}/plan-items/order
  { orderedPlanItemIds: [101, 104, 102], expectedVersion: 5 }
```

기존 GET 목표 목록은 현재 배열 응답이므로 envelope로 변경한다면 버전/호환성 이행 방안을 함께 제시해 주세요. 날짜순 fallback과 임시 로컬 순서의 서버 이전은 서버 계약 확정 후 별도로 처리합니다.

수용 기준: 목표 순서 변경 → 다른 기기에서 같은 순서 조회 → 목표 안 일정/반복/일회성 항목 혼합 순서 변경 → 날짜·과거 기록·다른 화면 순서 불변 → 동시 생성/삭제·충돌·재시도에서 데이터와 순서 보존.

## G-07. 개인 Task 검색의 새 Goal 필터 — 2026-10-19 추가, 미전달

현재 확인한 로컬 GoalTask API는 생성/연결/해제를 제공하지만 목표별 일회성 Task 목록 GET은 없고 TaskSearch 요청에도 `linkedGoalId` 필터가 없습니다. 계획 탭에서 반복 정의와 Goal에 연결된 일회성 할 일/일정을 빠짐없이 함께 보여주기 위한 요청입니다. 운영 부재를 직접 호출해 확인한 결과는 아니므로 기존 제공 경로가 있으면 계약을 알려주세요.

- 권장: 기존 `GET /api/v1/tasks/search`에 optional positive `linkedGoalId` 필터 추가. 기존 TaskSearchPage·cursor·정렬/상태/유형 필터를 유지하고 다른 조건과 AND로 적용해 주세요. 같은 역할의 목표별 GET이 이미 있다면 그 계약을 회신해도 됩니다.
- 본인 소유 개인 Goal과 개인 일회성 Task만 조회합니다. 다른 owner Goal은 기존 Goal 정책처럼 404이며 Workspace·반복 series·Goal/옛 개인 시스템 회차 연결 Task는 제외해 주세요. 새 Goal ID이며 D-Day ID 필터와 별개입니다.
- 날짜 없는 항목·미래 일정·완료 Task도 기존 상태/유형 필터에 따라 조회할 수 있어야 합니다. 첫 날짜/첫 페이지에 항목이 없다고 전체 목록이 빈 것으로 해석하지 않도록 `nextCursor`를 유지합니다.
- 응답의 안정적 Task ID·linkedGoalId·유형·상태·날짜·반복 정보는 기존 TaskResponse 계약을 재사용합니다. 필터 생략 시 기존 검색 동작은 유지합니다. Goal 보관 여부로 과거 Task를 삭제하거나 ID를 바꾸지 않습니다.
- 프론트는 회신/배포 확인 전 임의 필터를 보내거나 다른 날짜/첫 페이지 일부를 전체 목록으로 표시하지 않습니다. linkedGoalId 응답만 추가된 상태를 검색 필터 지원으로 취급하지 않습니다.

**상태:** 모바일 요구 문서화만 완료. 전달·계약 합의·백엔드 구현·배포는 미확인입니다.

## 계약 회신과 수용 기준

기존 D-Day·Task·recurrence 재사용 범위, 신규 엔터티/관계, 목표 `colorKey`, 날짜 선택·과거 입력·조회 범위/정렬·상태 변경·계정/게스트·멱등성·충돌·권한·삭제/보관·알림 정리 정책을 포함한 DTO/OpenAPI와 예시를 부탁드립니다. 아직 신규 경로명을 확정하지 않았습니다.

필수 검증: 목표 하나 아래 독립 반복 계획 둘 생성 → 각 회차 기본/최소 실천 → 일회성 Task 완료 → 이미 한 일 기록 → 목표 여정에 각 원본이 한 번만 등장 → 완료 취소 시 집계 갱신 → 계획/목표일 변경 후 과거 기록 보존 → 목표 달성 확인 및 미래 반복 처리.

기존 요청의 실천 결과·AI·알림·보안/소유권 공통 조건은 유지합니다. 이 문서와 원 요청을 무조건 별도 API 세트로 중복 구현하지 말고 통합 설계로 회신해 주세요. 백엔드 코드는 별도 저장소에서 진행합니다.
