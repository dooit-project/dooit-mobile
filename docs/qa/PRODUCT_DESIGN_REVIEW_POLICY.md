# Product Design 검토 정책

Last updated: 2026-10-24

화면 수정과 신규 사용자 기능이 구현 편의만으로 결정되지 않도록 Product Design 검토, 실제 화면 캡처와 검증 결과를 같은 작업 범위에서 관리한다.

## 적용 대상

다음 변경은 구현 전에 Product Design 검토를 거친다.

- 신규 화면, modal, drawer, sheet, tab, 주요 component
- 내비게이션·정보 구조·사용자 흐름 변경
- 주요 행동의 위치·위계·문구 변경
- 빈 상태·오류·복구·권한 제한 상태 추가
- 기존 화면의 밀도·색·타이포그래피·레이아웃을 눈에 띄게 바꾸는 작업

텍스트 오탈자, 보이지 않는 refactor, 테스트·API client·build script만 바꾸는 작업은 제외할 수 있다. 다만 사용자에게 보이는 결과가 달라지면 검토 대상으로 되돌린다.

구현이 없는 UI/UX 제안과 생성 이미지 수정에도 아래 기본 검토를 적용한다. 선택된 안의 국소 수정은 해당 안을 보정하며 매번 새로운 시각안 3개를 만들지 않는다. 시안 검토만으로 실제 앱 검증 완료를 선언하지 않는다.

## 모든 UI/UX 작업의 기본 검토

반복 지적의 기본 검사와 수정 루프는 [화면 개발의 기본 시각 검사](./UI_VISUAL_ACCEPTANCE.md)를 따른다. 실제 Web 변경에서는 새 좌표 보고서로 `check:ui-layout`을 실행하고 캡처의 광학적 정렬도 확인한다. 사용자의 재요청을 기다리지 않고 같은 범위에서 실패를 수정·재검사한다.

1. **대상과 근거 확인**: 현재 시안이나 실제 화면을 직접 열고 기존 제품 결정·공통 컴포넌트·토큰을 확인한다. Product Design이 제공되면 해당 작업의 스킬과 검토 기준을 읽고 적용한다. 제공되지 않는 도구나 열지 않은 Figma 파일을 사용했다고 표현하지 않는다.
2. **필요성과 위치**: 해당 화면이 필요한지, 다른 화면과 역할이 겹치는지, 핵심 기능을 찾기 쉬운 위치인지 확인한다. 예를 들어 오늘은 날짜별 실행, 계획은 목표와 연결 항목의 구성을 담당한다.
3. **행동 위계와 발견 가능성**: 자주 쓰는 행동은 직접 노출하고 덜 쓰는 관리 기능은 맥락에 맞는 메뉴로 묶는다. 공간 절약과 추가 탭의 비용을 함께 판단한다. 길게 누르기·드래그에만 기능을 숨기지 않으며 대체 조작과 취소·복구 경로를 정한다.
4. **시각 밀도와 일관성**: 중복 제목, 불필요한 빈 상태 문구, 과도한 여백, 큰 아이콘과 반복된 화살표를 확인한다. 색·아이콘·글자·간격은 역할에 맞게 일관되게 쓰고 항목 수가 늘거나 제목이 길어졌을 때의 처리도 정한다.
5. **접근성과 상태**: 터치 영역, 색 이외의 상태 표현, 대비, 글자 확대, 읽기 순서, 키보드·보조 기술 대체 조작을 검토한다. 시안에서는 위험과 구현 조건으로 기록하고 실제 작동 확인과 구분한다.
6. **외부 패턴 비교**: 관련 공식 디자인 가이드와 실제 서비스의 공식 사용 안내에서 해당 문제의 패턴을 확인한다. 예쁜 화면을 그대로 복제하기보다 Dooit의 사용자 목적에 맞는 이유와 단점을 기록한다. 이미 확인한 자료는 재사용할 수 있으며 현재 동작을 주장하거나 불확실한 부분은 최신 자료로 확인한다.
7. **결론 기록**: 유지할 것, 바꿀 것, 이유, 미확인 상태를 짧게 남긴다. 추천은 설계 판단인지, 사용자 관찰 결과인지 구분한다. 도구 사용 자체를 품질 보증으로 취급하지 않는다.

화면을 구현하거나 수정해 사용자에게 결과를 전달할 때는 확인한 실제 캡처를 답변에 직접 표시하고, 이미지가 열리지 않을 때를 위해 파일 링크도 제공한다. 시안과 실제 화면, mock 데이터, 촬영 환경을 구분한다. 표시용으로 캡처를 잘랐다면 그 사실을 밝히고 원본도 보존한다. 화면을 캡처하지 못한 경우에는 그 이유를 명시한다.

선택지가 많은 폼은 **기본 상태와 편집 중 상태를 따로** 캡처하고, 동시에 노출되는 선택 그룹/조작 수·현재 값 확인 가능성·선택/복귀에 필요한 탭·스크롤 비용을 기록한다. 고정된 개수 제한을 만들기보다 사용자의 당장 할 일에 필요하지 않은 그룹이 경쟁하는지 판단한다. 선택지의 경계·색·키보드만 보정하고 핵심 밀도가 남아 있으면 전체 UX는 수정 필요로 판정한다. 접근성/기능 검사 통과를 밀도 문제 해결로 확대하지 않는다.

### 참고 자료와 확인 수준

- 추가 프론트엔드 검토는 프로젝트에 설치한 [Anthropic frontend-design](../../.agents/skills/frontend-design/SKILL.md), [Vercel React Native Skills](../../.agents/skills/react-native-skills/SKILL.md), [Vercel Web Design Guidelines](../../.agents/skills/web-design-guidelines/SKILL.md)를 해당 작업에 맞춰 적용한다. 시각 위계·문구의 추가 검토가 필요하면 frontend-design을, React Native 구현에 관련 native 규칙이 있으면 해당 규칙을, Web UI 검토에서는 최신 Web Interface Guidelines를 확인한다. [도입·시범 검토와 제한](../design/DESIGN_SKILLS_ADOPTION_2026-11-06.md)을 따른다. 플랫폼에 맞지 않는 규칙이나 새 의존성을 자동 적용하지 않는다. 원문 참고, 설치된 스킬 적용, 자동 검사와 실제 화면 검증을 구분해 기록한다. 사용자 선택 시안과 제품 제약이 우선이다.

- 공식 가이드 예: [Material의 목록 조작](https://m1.material.io/components/lists-controls.html), [메뉴](https://m1.material.io/components/menus.html), [탭](https://m1.material.io/components/tabs.html). 이 링크는 구버전 Material 자료이므로 최신 컴포넌트 사양을 주장하는 근거로 쓰지 않는다.
- 운영 서비스 예: [Things 이동 기능](https://culturedcode.com/things/support/articles/9651894/), [Todoist 정렬·그룹](https://www.todoist.com/help/todoist/features/sort-or-group-tasks-in-todoist-WFWD0hrb). 기능 설명 자료를 읽은 것과 앱을 직접 조작한 것을 구분한다.
- Figma는 아래 사용 기준을 따른다. 파일을 직접 열었다면 파일·프레임 링크와 확인 범위를 기록한다. Figma 미사용은 검토 누락을 뜻하지 않는다.
- 실제로 읽은 출처만 사용했다고 기록하고, 참고한 규칙과 Dooit에 적용한 판단을 연결한다.

### 작업별 최소 기록 양식

```md
- 대상/사용자 목적:
- 확인한 화면·시안: (파일 또는 링크, 생성 이미지/실제 캡처 구분)
- 적용한 스킬·도구:
- 참고 자료와 적용 이유: (직접 확인한 링크, 확인일 또는 기존 기록)
- 유지 / 변경 / 이유:
- 상호작용·접근성 위험과 구현 조건:
- 실제 검증 범위 / 미확인 또는 보류한 항목:
```

사용자가 검증을 보류하도록 요청한 경우 그 범위와 사유를 작업 기록에 남기고 요청을 따른다. 보류를 통과로 기록하지 않으며, 문서·시안 검토와 실제 화면 감사·테스트 완료를 혼동하지 않는다.

## 화면 작업의 스킬 검토와 수정 루프

화면 구현·수정·시안 보정에서는 사용자 요구와 선택된 원본 시안, 공통 컴포넌트, 화면 역할과 사용자 흐름을 먼저 확인한다. Product Design index의 라우팅을 따르고 시각 정렬·긴 문구·터치 영역과 실제 화면 비교를 기본으로 확인한다. 설치된 다른 스킬은 작업 범위·플랫폼·위험에 맞게 선택하며, 모든 스킬을 매번 실행하거나 관련 없는 스킬의 미실행 사유를 하나씩 적지 않는다. 사용한 스킬과 방법·발견 사항·중요한 미확인 항목을 기록하며 설치만으로 통과를 주장하지 않는다. 사용자의 명시적 요청과 필수 검증 규칙이 이 선택 기준보다 우선한다.

1. **Product Design부터:** index의 라우팅에 따라 현재 화면·흐름 검토는 `audit`, 의미 있는 새 시각 방향과 선택지는 `ideate`, 선택한 이미지의 구현은 `image-to-code`를 쓴다. 세 스킬을 무조건 모두 실행하거나 기존 선택안의 작은 보정마다 새 시안을 만들지는 않는다. 새 정보 구조의 3안 선택 기준은 유지한다.
2. **시각 디자인:** 정보 위계·타이포·간격·문구·디자인 완성도의 추가 검토가 필요한 경우 Anthropic `frontend-design`과 Impeccable의 관련 지침을 활용한다. 사용자 시안과 사실이 우선이다. Impeccable context launcher·detector의 실행 결과와 참고 문서 검토를 구분한다. 외부 engine 다운로드, 자동 hook 및 live 편집은 해당 도구의 실제 동작과 권한을 먼저 확인하고 별도 승인이나 사용자 요청 없이 활성화하지 않는다. 실행할 수 없다면 원인과 미검증 항목을 남기고 설치만으로 통과시키지 않는다.
3. **패턴·구현:** UX 패턴 탐색에는 UI UX Pro Max를, 테마·공통 컴포넌트 변경에는 `expo-design-system`을, 관련 native 구현에는 Vercel React Native를 활용한다. Web UI 검토에는 `web-design-guidelines`의 최신 지침을 적용한다. 검색 결과는 해당 SDK·플랫폼·제품 맥락에 맞게 판단하며 버전이나 OS가 다른 권고는 그대로 일괄 적용하지 않는다.
4. **경계 상태:** 실제 허용 길이에 맞는 긴 제목, 빈 목록, 여러 항목, 작은 화면, 확대 글자 등 변경과 관련된 경계 상태를 확인한다. 심화 점검이 필요하면 `break-ui` 지침을 참고한다. 테스트 데이터를 실제 기록처럼 표시하지 않고, 임시 도구나 데모 토글을 제품 화면에 남기지 않는다. 사용자 요청으로 수정까지 허용된 경우 발견 후 같은 범위를 계속 고친다.
5. **수정 → 재검증:** 영향을 받는 정상·완료·빈 상태·오류/복구를 재현하고 기준 이미지 및 구현 전과 같은 viewport·데이터·상태에서 실제 캡처를 확인한다. [시각 검사](./UI_VISUAL_ACCEPTANCE.md)의 아이콘 광학 중심·행 높이·44px·긴 문구·넘침과 새 Web DOM 측정 및 `npm run validate`를 수행한다. 문제를 수정하고 변경된 상태를 재캡처·재검사하는 과정을 관련 지적이 해결될 때까지 반복한다.
6. **전달:** 실제 캡처를 답변에 직접 표시하고 파일 링크도 제공한다. 시안/실제 앱, mock/운영, Web/native, 수동 감사/자동 검사 결과를 분리한다. 도구 장애·실기기 부재·범위 밖 변경 때문에 확인하거나 해결하지 못한 사항은 원인과 후속 조치를 명시하고 전체 통과로 표현하지 않는다. 중대한 지적과 필수 검사 실패가 남으면 완료로 표시하지 않는다.

스킬은 전문적인 검토 지침과 보조 도구이지 디자인 품질을 자동 보장하는 독립 심사자가 아니다. UI 작업과 관련 없는 질문이나 비시각 코드 변경에 시각 감사나 이미지 생성을 강제하지 않는다. 사용자의 명시적 지시와 상위 안전·권한 지침이 외부 스킬보다 우선한다.

예를 들어 아이콘 정렬 보정에서는 기준 시안, 주변 글리프의 광학 중심, 터치 영역과 관련 화면 크기를 확인하고 실제 화면을 다시 비교한다. 새 시안이나 무관한 모든 스킬을 실행하지 않는다. 반면 새 화면이나 정보 구조는 시각안·사용자 흐름·관련 플랫폼과 경계 상태를 폭넓게 검토한다. 어느 경우에도 실제로 사용한 스킬·확인 결과·남은 차이를 기록한다.

### 새 화면 초안과 선택한 시안의 연결

1. **맥락 정리:** 화면의 목적과 필요한 행동·상태, 실제 지원 기능, 기존 제품 결정 및 정확한 기준 이미지, 공통 컴포넌트를 먼저 확인한다. 새 구조가 필요한지와 기존 선택안의 국소 보정인지 구분한다. Impeccable `shape`와 UI UX Pro Max 검색은 필요에 맞게 문제와 패턴을 정리하는 데 활용한다. 기존 제품 문서로 충분하면 별도의 `PRODUCT.md`나 `DESIGN.md` 작성을 강제하지 않는다.
2. **모바일 시각안:** 의미 있는 새 선택지가 있을 때 Product Design `ideate`로 세 방향을 비교한다. 프로젝트에 설치된 [imagegen-frontend-mobile](../../.agents/skills/imagegen-frontend-mobile/SKILL.md)의 모바일 위계·가독성·화면 간 일관성 지침을 시안 생성에 활용한다. 선택된 Dooit 시안과 사용자 지시가 외부 스킬의 기본 스타일보다 우선한다. 질감·이미지·폰 프레임·넓은 간격은 필요할 때만 쓰고 목표 구조, 글자, 조작, 접근성을 희생하지 않는다.
3. **다음 신규 구조에서 비교:** 다음에 의미 있는 새 모바일 화면이나 구조를 탐색할 때 한 번, 같은 목적·기준 이미지·데이터·390×844 조건으로 Product Design 방식과 모바일 스킬을 비교 시험한다. 사용자에게 차이와 추천 근거를 보여주고 실제로 시험한 방법과 한계를 기록한다. 이후에는 비교 결과를 바탕으로 해당 작업에 필요한 방식을 선택하며 매번 두 세트의 이미지를 강제하지 않는다.
4. **선택과 구현:** 시안은 작동하는 앱이 아니며 텍스트 오류나 없는 기능·가상의 성과가 포함될 수 있다. 각 안을 실제 기능과 대조하고 생성 이미지임을 명시한다. 선택된 이미지의 경로와 결정 이유, 고정 요소·변경 범위를 기록하고 선택 없이 새 구조를 구현하지 않는다. 구현은 필요에 따라 Product Design `image-to-code`와 기존 공통 컴포넌트를 사용한다.
5. **결과 확인:** 구현 후 같은 조건의 실제 화면을 캡처해 선택 시안과 비교하고 위의 검토·수정 루프를 수행한다. 시안 검토, 실제 화면 검증, 자동 검사는 별도로 기록한다. Figma는 기존 사용 기준에 해당할 때 사용한다.

## 기본 절차

1. **문제와 목표 정의**
   - 대상 사용자, 화면, 해결할 불편과 성공 조건을 한 문단으로 정리한다.
   - 현재 화면·유사 흐름·design token·공통 component를 먼저 확인한다.
2. **구현 전 Product Design 검토**
   - 기존 패턴 안의 작은 변경은 구조·위계·문구를 검토한다.
   - 신규 화면이나 구조가 여러 방식으로 가능한 경우 390×844 기준 시각안 3개를 비교하고 선택 전 구현하지 않는다.
   - 기능을 보여주기 위한 불필요한 card·badge·tab·설정은 추가하지 않는다.
3. **구현**
   - 선택한 시각 목표와 기존 design system을 따른다.
   - 정상 상태뿐 아니라 loading·empty·error·disabled·부분 성공·복구를 함께 구현한다.
4. **구현 후 실제 화면 감사**
   - mock 또는 재현 가능한 데이터로 실제 앱 화면을 새로 캡처한다.
   - 캡처를 직접 확인한 뒤 UX, 시각 완성도와 접근성 위험을 화면 단계별로 기록한다.
   - 기존 캡처나 파일명만 보고 통과 판정하지 않는다.
5. **수정과 재검증**
   - 치명적·높음 문제는 같은 변경에서 수정한다.
   - 중간·낮음 문제는 로드맵 또는 관련 audit에 근거와 함께 남긴다.
   - `npm run validate`와 영향 플랫폼 검증을 완료한다.

## 로컬 브라우저 선택 기준

OpenAI의 [Browser 공식 문서](https://learn.chatgpt.com/docs/browser)는 ChatGPT 데스크톱 앱의 내장 브라우저가 사용자와 ChatGPT가 웹사이트와 로컬 웹 앱을 같은 화면에서 보며 preview, 시각 feedback과 interaction 검증을 수행하는 surface라고 설명한다. 일반 browser profile이나 기존 tab을 그대로 사용해야 할 때는 browser extension을 사용하도록 구분한다.

Dooit의 로컬 Web 검증은 다음 순서를 기본으로 한다.

1. **ChatGPT 앱 내장 브라우저**
   - localhost의 Expo Web 화면, mock flow, responsive viewport, keyboard focus와 실제 캡처 검증의 기본 surface다.
   - 별도 Chrome profile이나 기존 로그인 상태가 필요하지 않은 개발·디자인 QA에 우선 사용한다.
2. **Chrome 확장 연결**
   - 기존 Chrome tab, 로그인 session, extension, 일반 browser profile 또는 Chrome 고유 동작이 검증 조건일 때 사용한다.
   - 사용자가 Chrome을 요청하거나 같은 Chrome 상태를 이어서 확인해야 할 때도 이 경로를 유지한다.
3. **로컬 Playwright**
   - 선택한 browser surface가 로컬 주소를 열지 못하고 연결·주소·server 상태 복구로도 해결되지 않을 때 사용하는 자동화 fallback이다.
   - 전환 사유, viewport, browser channel, 캡처와 console 결과를 해당 audit README와 `design-qa.md`에 기록한다.

어떤 surface를 사용해도 source visual과 implementation capture를 같은 viewport와 상태로 비교하고, 실제로 확인하지 않은 interaction이나 접근성 동작은 통과로 기록하지 않는다.

## 검토 기준

### 사용성

- 첫 화면에서 현재 위치와 다음 행동이 분명한가
- 자주 쓰는 행동이 불필요한 중간 화면을 거치지 않는가
- 저장·완료·이동 결과와 실패·재시도가 같은 맥락에서 이해되는가
- 사용자가 중단·뒤로 가기·건너뛰기를 안전하게 할 수 있는가
- 빈 상태가 시작 방법을 설명하고 과도한 기능을 권하지 않는가

### 미감과 일관성

- spacing, alignment, typography가 정보 위계를 먼저 만드는가
- divider와 surface tint로 충분한 곳에 border·shadow를 남용하지 않는가
- card 안에 card가 중첩되거나 모든 row가 독립 card처럼 보이지 않는가
- Dooit의 white surface, muted blue·sage·amber와 조용한 밀도를 유지하는가
- Android·iOS·Web에서 같은 역할이 같은 시각 언어를 쓰는가

### 접근성

- 핵심 touch target이 최소 44pt인가
- 색 이외의 label·icon·state로 선택·완료·오류를 전달하는가
- screen reader 이름·역할·상태와 읽기 순서가 자연스러운가
- keyboard focus, Escape, Android back과 modal focus 복귀가 동작하는가
- 320px, 390px, 430px와 font scale 1.5에서 핵심 행동이 유지되는가

## Figma 사용 기준

Figma는 매 화면 변경의 필수 단계가 아니다. 다음 경우에만 Product Design 검토와 함께 사용한다.

- 사용자가 Figma 산출물 또는 검토 보드를 명시적으로 요청한 경우
- 여러 화면의 흐름·비교안을 팀과 공유해야 하는 경우
- design token·component·variant를 library로 관리해야 하는 경우
- 캡처와 발견 사항을 장기 보존할 시각 보드가 필요한 경우

단순한 구현 전 검토와 구현 후 감사는 저장소의 Markdown, 실제 캡처와 코드가 원본이다. Figma를 사용하더라도 저장소의 판정과 링크를 함께 갱신한다.
