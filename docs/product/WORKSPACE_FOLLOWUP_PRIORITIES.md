# Workspace 후속 기능 우선순위

> 최종 갱신: 2026-08-23

Workspace 핵심 일정 공유 이후 제안된 초대 거절, 하위 작업, 주간 리포트의 1차 제품 우선순위를 정한다. 실제 사용자 인터뷰나 사용 지표를 대신하는 문서가 아니며, 현재 흐름의 완결성·대체 방법·API 영향·화면 복잡도를 기준으로 출시 전 범위를 제한한다.

## 판단 기준

| 기준        | 확인 질문                                                         |
| ----------- | ----------------------------------------------------------------- |
| 흐름 완결성 | 사용자가 시작한 흐름을 수락 외의 정상적인 방법으로 끝낼 수 있는가 |
| 사용 빈도   | 핵심 일정 공유 과정에서 반복적으로 만나는 문제인가                |
| 대체 가능성 | 현재 Task·설명·별도 일정으로 무리 없이 대신할 수 있는가           |
| 계약 복잡도 | scope·권한·반복·삭제·동기화 규칙을 새로 만들 필요가 큰가          |
| 화면 복잡도 | 현재 일정·D-Day·멤버 구조에 정보와 행동을 얼마나 추가하는가       |

## 결정

| 후보        | 우선순위             | 결정                                                                  |
| ----------- | -------------------- | --------------------------------------------------------------------- |
| 초대 거절   | P1, 백엔드 계약 직후 | 구현한다. PENDING 초대를 수락하지 않으면 목록에서 정리할 방법이 없다. |
| 하위 작업   | 보류                 | 출시 범위에서 제외한다. 별도 Task나 설명으로 우선 대체한다.           |
| 주간 리포트 | 탐색                 | 출시 범위에서 제외한다. 반복 사용과 완료 데이터의 필요성을 먼저 본다. |

### 초대 거절

현재 받은 초대에는 `초대 수락`만 있어 원치 않거나 잘못 온 초대가 계속 남는다. 이는 새 기능 확장보다 기존 흐름의 종료 행동이 빠진 문제에 가깝다.

- 초대 카드에는 `수락`을 주요 행동, `거절`을 보조 행동으로 함께 둔다.
- 거절은 되돌리기 어려우므로 확인 dialog에서 Workspace 이름을 다시 보여준다.
- 성공하면 받은 초대 cache에서 즉시 제거하고 참여 중인 공간에는 추가하지 않는다.
- 실패하면 카드를 유지하고 재시도 가능한 inline 오류를 표시한다.
- 초대가 이미 취소·수락된 `404` 또는 `409`이면 목록을 새로고침하고 현재 상태를 설명한다.
- API가 준비되기 전에는 동작하지 않는 버튼을 먼저 노출하지 않는다.

### 하위 작업

하위 작업은 단순한 UI 행 추가가 아니다. 부모 완료 시점, 반복 occurrence 상속, D-Day 연결, 개인/Workspace 이동, 정렬·검색·알림과 삭제 정책이 모두 필요하다. 현재 일정 공유 출시를 지연시킬 근거는 부족하다.

다음 신호 중 하나가 반복 확인되면 다시 검토한다.

- 사용자가 하나의 목표를 여러 Task로 만들고 제목 접두어로 묶는 패턴이 잦다.
- Task 설명을 체크리스트처럼 사용하는 요구가 반복된다.
- Workspace 일정의 책임 분담을 한 Task 안에서 관리해야 한다는 피드백이 누적된다.

재검토 전에는 하위 작업용 임시 local-only 모델이나 Workspace 전용 UI를 만들지 않는다.

### 주간 리포트

주간 리포트는 핵심 기록·공유가 안정된 뒤 도움이 되는 파생 화면이다. 현재는 완료 수치만 강조하면 생산성을 평가하는 인상을 줄 수 있고, 빈 데이터 상태가 홈과 Workspace의 정보 밀도를 높인다.

재검토 시 먼저 확인할 질문:

- 사용자가 지난주 완료·미완료를 실제로 되돌아보는가?
- 개인과 Workspace 리포트를 분리해야 하는가?
- 완료 개수 외에 이월, 반복, D-Day 진척 중 어떤 정보가 행동으로 이어지는가?
- 자동 push·메일 요약이 필요한가, 사용자가 열어보는 화면이면 충분한가?

사용 근거가 생기기 전에는 새 탭이나 홈 요약 카드를 추가하지 않는다.

## 구현 순서

```text
초대 거절 API·권한 계약
  → mock·API client·cache mutation
  → 받은 초대 카드의 수락/거절 위계
  → Product Design 캡처 점검
  → 320px·글자 확대·Web keyboard·스크린 리더 검증
  → real API smoke
```

공유 UI가 실제로 바뀌는 단계에서는 [`WORKSPACE_UI_FLOW.md`](./WORKSPACE_UI_FLOW.md)의 캡처 순서로 Product Design 점검을 먼저 수행한다.
