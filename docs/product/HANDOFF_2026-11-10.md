## 사용자와 합의한 제품 방향

- 목표는 방향을 제공하고 반복 계획·일회성 할 일·일정은 목표 아래에서 이어진다. 목표 달성률을 임의로 계산하지 않고 기록 없는 성과·감정을 만들지 않는다.
- 반복 계획의 기본 행동은 지속 가능한 크기로 정한다. 별도의 작은 행동은 필요한 사용자만 설정한다. 하루를 쉬어도 실패로 표현하지 않는다.
- 기본 상태의 완료는 한 번 체크한다. 작은 행동을 준비한 경우에만 오늘의 행동을 바꿀 수 있게 하며, 전환은 완료가 아니다. 선택한 행동은 전체 문장을 확인할 수 있어야 한다. 처음 시안의 ‘3개만 하기’는 숫자형 예시일 뿐이다.
- 오늘의 선택이 내일이나 계획 원본을 자동으로 바꾸지 않는다. 기록은 확인된 실제 선택에 근거한다. UNKNOWN을 STANDARD/MINIMUM으로 추정하지 않는다. 행동 전에 고르거나 행동 후 체크 전에 바꿀 수 있고, 잘못된 기록을 취소할 수 있어야 한다.
- ‘1번 축소’는 인터랙션 방향 합의다. 보조 조작의 위치·문구·320px 긴 제목은 보정 시안과 실제 화면에서 확인해야 한다. 사용자 선호나 효과에 대한 실측 데이터는 아직 없다.

## 현재 기준선

- 계획 화면의 목표별 최근 기록과 더 보기/접기는 `f708363`으로 커밋했다. [21개 mock 기록과 초점 검토](../audits/plan-inline-history-recheck-2026-11-08/README.md)는 운영 API나 native 검증이 아니다.
- 기존 오늘 항목에서는 작은 행동으로 생성된 연결 Task 제목이 사용자 선택 전에도 표시될 수 있다. [mock 캡처](../design/today-routine-choice-2026-11-08/current-390.png) 및 `src/features/today/today-goal-items.ts` 참고. 기존 체크는 일반 Task 완료를 호출하며 mock 연결 결과는 UNKNOWN이다.
- 클라이언트의 `src/features/goals/goal-plan-form-values.ts`와 `src/types/goal-plan.ts`는 기본·작은 행동을 필수로 취급한다. 로컬 백엔드 `8d11333`도 생성·수정 DTO의 `minimumAction`과 버전 텍스트가 필수다. 운영 API에서 해당 버전이 배포되었는지는 직접 확인하지 않았다.
- 계획 아래 새 Goal의 일회성 할 일·일정 연결, 운영 API, Android/iOS, 확대 글자, 스크린리더 및 오류 화면은 이번 작업으로 완료된 것이 아니다.

## 다음에 할 일

1. **연결 상태와 계약 확인:** 목표 계획→오늘→체크→상세·돌아보기의 현재 코드, 연결 Task·회차 스냅샷·다음 행동 및 캐시를 살핀다. 저장된 다음 행동을 평소 행동으로 덮어쓰지 않는다. 로컬 백엔드 제목 생성과 기존 단일 Task 완료의 UNKNOWN 경로를 확인하고, 운영 상태는 별도로 확인한다.
2. **표시·기록 정확성 우선:** 사용자가 작은 행동을 고르지 않았는데 작은 행동이 기본처럼 표시되는 문제를 해결한다. 한 화면의 제목만 바꾸어 상세·달력·기록과 서로 다른 사실을 표시하지 않는다. 선택한 결과와 Task 완료·취소·오류·버전 충돌·중복 제출을 연결하고 기존 UNKNOWN을 보존한다. 서버 계약이 막는 범위는 구현했다고 주장하지 않는다.
3. **선택적 입력:** 작은 행동이 없는 계획의 생성·조회·수정·회차·기록에 필요한 백엔드 계약을 확인한다. [요청 초안](../api/API_GOAL_OPTIONAL_MINIMUM_REQUEST_2026-11-10.md)을 사용해 필요 시 사용자가 전달할 수 있게 하며, 임의의 최소 행동을 생성하거나 비어 있는 결과를 저장하지 않는다.
4. **1번 보정:** 기존 목표 묶음을 유지하면서 기본 체크 1회, 별도 대안이 있을 때의 가벼운 진입, 선택/복귀를 보정한다. 새 큰 버튼·매회 완료 시트·별도 페이지를 기본으로 추가하지 않는다. 필요하면 보정 이미지를 사용자에게 보여주고 같은 데이터·뷰포트의 실제 화면과 비교한다.
5. **검증 및 인계:** 정상·긴 제목·여러 반복·대안 없음·다음 행동·기존 UNKNOWN·완료 취소·저장 오류·동시 수정·날짜 전환을 다룬다. Web 변경은 320/390/430 실제 화면과 DOM 검사를 수행하고 `npm run validate`를 실행한다. 스킬별 실제 적용·결과와 native/운영/접근성 미확인을 기록한다.

의미 있는 구조 변경에 새로운 선택지가 생기면 저장소 규칙을 따른다. 기존 보정 작업을 위해 새로운 3안을 무조건 만들지는 않는다. 사용자 승인 없이 커밋·푸시하지 않는다.
