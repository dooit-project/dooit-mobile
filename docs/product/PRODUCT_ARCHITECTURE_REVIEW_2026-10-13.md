# Dooit 화면 역할과 탐색 구조 재검토

검토: 2026-10-12–13 · 상태: 구조·스타일 조합 사용자 선택, 상세 검토·구현 전

## 사용자 선택 보충

2026-10-13 사용자가 [TO-BE 보드](../design/to-be-2026-10-13/README.md)의 1번 구조 + 2번 스타일을 선택했다. 즉 오늘·계획·돌아보기 구조에 간결한 목록·타이포·여백을 적용한다. 아래 대안 표는 비교 근거로 보존하며 재선택 대기가 아니다. [일상 반복 행동 점검](./DAILY_SYSTEM_FIT_REVIEW_2026-10-13.md)의 운동·영단어·순환 동기 문구를 조합 시안에 반영한다.

후속 제품 범위: [목표·실행 계획·지나온 길](./GOAL_JOURNEY_EXPERIENCE.md)을 기준으로 계획의 내 목표→목표 상세를 핵심 진입으로 둔다. 목표 아래 여러 반복 계획과 일회성 노력을 연결하고 돌아보기와 목표 상세가 같은 여정 원본을 보여준다. 이전에 D-Day를 주변 도구로만 둔 추천은 범용 Goal로의 확장·기존 데이터 이행 관점으로 수정한다.

## 추천 방향과 확정된 결정

**장기 구조는 `오늘 · 계획 · 돌아보기`를 우선 추천한다.** 오늘은 실행, 계획은 앞으로 할 일과 아직 정하지 않은 바람, 돌아보기는 실제로 해온 일을 담당한다. 계정·설정 묶음이 세 자리 중 하나를 차지하는 현재 구조보다 사용자가 원하는 제품의 반복 흐름을 잘 드러낸다는 판단이다. 달력은 계획의 눈에 보이는 진입으로 두되, 오늘에서도 `달력` 버튼 한 번으로 열 수 있게 한다. 접근 경로를 숨기는 축소는 하지 않는다.

이는 사용자 이용 데이터로 검증된 결론이 아니다. 일정 탐색이 주된 사용이라면 `오늘 · 달력 · 계획 · 돌아보기` 4탭이 더 적합하다. 아래 세 안을 비교했고 사용자가 B에 해당하는 보드 1번의 구조를 선택했다. 달력 접근성은 실제 시안에서 계속 검증한다. 앞선 `오늘 · 달력 · 전체` 제안은 현재 구조를 적게 바꾸는 전환안으로 남기고, 최종 구조 추천을 이 문서로 갱신한다.

사용자가 이미 선택한 것은 [실행 시각안 3번](../design/personal-systems-2026-10-12/README.md)의 **필요할 때 열리는 제안형 실행 sheet**다. 이 상호작용은 유지한다. 이미지 속 주간 달력·하단 탭·나머지 화면까지 승인된 것으로 해석하지 않는다. 현재 Today에는 주간 달력이 없다.

## 근거와 가정

- 현재 구현: `6fd5293` 기준 모바일 클라이언트, 문서 미커밋 변경 포함. [이번 실제 화면 감사](../audits/product-architecture-2026-10-12/README.md)와 [앞선 UI 감사](../audits/ui-structure-2026-10-12/README.md)를 구분해 연결한다.
- 우선 사용자 가정: 개인의 일상 실행과 지속 가능한 시스템을 만들고 싶은 사람. 일반 일정·할 일 이용도 유지한다. 공유 공간 이용 비중·달력 사용 빈도·이탈 원인은 확인하지 못했다.
- 경쟁 앱은 공식 제품·도움말의 공개 설명을 조사했다. 설치 앱의 최신 전체 여정을 직접 감사한 결과가 아니다. 디자인 자료는 판단 원칙의 참고이며 Dooit에서의 효과를 증명하지 않는다.
- 이번 직접 확인은 mock Web, 게스트, 390×844, light다. 실기기·인증된 Workspace·실제 API·오류 복구와 대량 데이터는 별도 검증 대상이다.

## 지금 구조에서 먼저 풀 문제

1. **핵심 경험과 주요 목적지가 다르다.** 현재 더보기는 계정·도구 중심이고 완료 기록도 그 안에 있다. 앞으로 실천을 돌아보는 일이 제품의 핵심이라면 독립적인 목적지로 다룰 이유가 있다.
2. **목표가 곧 날짜가 된다.** 목표 화면의 실제 입력은 D-Day 이름·날짜다. 날짜 없는 바람을 받아들이려면 이 화면을 전체 목표의 대표로 쓸 수 없다.
3. **계획과 회고의 의미가 섞인다.** `/today/review`는 과거 회고가 아니라 오늘의 계획·기록함 정리다. 완료 기록과 하루 마감도 분리되어 있다. 경로명보다 사용자가 예상하는 행동으로 묶어야 한다.
4. **같은 탐색이 여러 번 나온다.** 하단 탭, drawer, 더보기가 겹친다. 반면 작성 dock은 탭 위에 별도 층을 만든다. 메뉴가 많아서보다 역할이 중복되어 복잡하다.
5. **빈 상태가 화면 전체를 설명에 쓴다.** 안내 배너·큰 빈 공간·빈 상태 CTA가 반복된다. 기능이 있어도 실제 내용이 적을 때 도구 상자처럼 보인다.
6. **시각 문제와 기능 오류를 구분해야 한다.** 앞선 mock 감사에서 할 일로 입력한 날짜 포함 문장이 일정으로 저장되고 성공 안내는 할 일이라고 했다. 이 문제는 색·아이콘 개선으로 해결되지 않는다.

## 탐색 구조 세 안

| 안                 | 하단 목적지                   | 달력 접근                               | 장점                                         | 비용·선택 조건                                                                               |
| ------------------ | ----------------------------- | --------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------- |
| A — 전환안         | 오늘 · 달력 · 전체            | 하단 1회                                | 현재 사용자 경로를 가장 적게 바꿈            | 전체가 다시 기능 창고가 될 위험. 회고는 하위에 남음. 신규 증거 기능 준비 전 임시 구조에 적합 |
| B — 우선 추천      | 오늘 · 계획 · 돌아보기        | 오늘의 달력 버튼 1회, 계획에서 달력 1회 | 실행→준비→증거의 역할이 명료, 계정 탭 제거   | 계획이 복잡해지지 않아야 함. 달력 발견 가능성·한 손 조작을 검증해야 함                       |
| C — 일정 사용 우선 | 오늘 · 달력 · 계획 · 돌아보기 | 하단 1회                                | 달력 접근 보존, 나머지 핵심 흐름도 직접 노출 | 4개 목적지가 필요할 만큼 각각 역할·콘텐츠가 있어야 함. 계획과 달력의 중복 설명 필요          |

B의 계획은 거대한 대시보드가 아니다. `내 시스템` 한 행, `보관한 생각·할 일` 목록, 명시적인 `달력` 진입을 기본으로 한다. 아직 실행하지 않을 바람을 그대로 보관할 수 있다. 공통 header의 검색·계정 진입과 계획의 공간 전환은 보이게 둔다. 세 안의 표는 시각안 선택을 대신하지 않는다.

명칭은 **오늘을 유지**하는 편을 추천한다. 정말 오늘의 행동만 보여주면 이해하기 쉽다. `홈`은 범위가 넓고 `실행`은 일정·휴식까지 행동을 강요하는 인상을 줄 수 있다. 화면 안에 큰 dooit 로고 대신 `오늘`과 짧은 날짜를 사용한다. `계획`은 잠정 명칭이며, 날짜 없는 생각도 보관할 수 있다는 설명과 이름 이해도 검증이 필요하다.

## 선택된 3번을 전체 경험에 연결하기

1. **처음:** 오늘의 작은 초대 또는 계획에서 바람을 적는다. 건너뛰기·그대로 보관하기 가능. 한 계획부터 쉽게 시작하되 목표 아래 여러 반복 계획과 일회성 행동을 만들 수 있다.
2. **설정:** 시작 조건·기본 행동·최소 행동을 수정한다. 예: 식사 후 / 25분 작업 / 프로젝트 열고 5분. 첫 행동과 다음 실행을 확인한다.
3. **오늘:** 목록에 시스템 이름·오늘 행동·지난 다음 행동 한 줄을 보인다. `시작하기`를 누르면 3번 sheet가 열린다. 목록 단계에서도 무엇을 하려는지 알 수 있어야 한다.
4. **제안 sheet:** 기본 행동·작게 시작하기를 동등한 선택으로 제공하고 `이번에는 쉬기`를 보조 행동으로 둔다. 닫기는 상태를 바꾸지 않는다. 시작 버튼은 완료 기록을 생성하지 않는다.
5. **실천 후:** `실천했어요`로 확인한다. 실제 한 일과 다음 행동은 선택 입력, 완료 저장을 막지 않는다. 진행 중 앱을 나갔다고 실천 시간을 추정하지 않는다.
6. **일주일 뒤:** 날짜·회차 집계와 실제 메모를 보여준다. 각 요약의 원본 기록을 열 수 있다. `그대로 이어가기`·`조정하기`로 연결한다.
7. **빠진 뒤:** 이유 선택은 선택 사항. 시간대·행동 크기·첫 단계 중 한 가지 조정만 제안한다. 지난 회차를 전부 오늘로 옮기지 않는다.

sheet에 시스템 전체 편집·주간 회고까지 넣지 않는다. 긴 입력은 별도 화면으로, sheet는 당장 할 행동 선택에 사용한다. native back, Web Escape, 닫은 뒤 focus 복귀와 큰 글꼴에서 스크롤을 검증한다.

## 다독임·명언은 어디에 둘까

별도 하단 `동기부여` 탭은 만들지 않는다. 오늘의 짧은 여백, 실행 sheet, 완료 후, 돌아보기의 끝처럼 **다음 행동을 가리지 않는 자리**에 한 문장만 둔다. 사용자가 원하면 `잠깐 쉬어가기` 화면을 열어 더 읽거나 최소 행동·휴식을 선택할 수 있게 한다.

- 2026-10-13 사용자 요청 보충: 일반 응원/명언은 새 날 또는 4시간 이후 재방문 시 바뀌고 읽는 동안 유지하는 정책을 제안한다. 직접 다른 문장 보기·최근 중복 방지·숨기기를 포함한다. 상세는 일상 반복 행동 점검 문서를 따른다. 완료 feedback은 해당 기록에 대한 사실 한 줄로 별도 취급한다.
- `덜 보기`·`숨기기`를 제공하고 계정별 로컬 설정으로 시작한다. 명언 출처 표시는 열어 확인할 수 있게 한다.
- 자체 문구 예: “원하는 일을 아직 잘하지 못해도, 오늘 조금 시작할 수 있어요.” / “오늘은 쉬어가도 괜찮아요. 다음에 돌아올 자리는 남아 있어요.”
- 기록 기반 예: 실제 3회일 때만 “이번 주에 세 번 프로젝트로 돌아왔어요.” 사용자가 피곤함을 기록하지 않았다면 피곤했다고 쓰지 않는다. 계획한 5분을 실제 수행 시간으로 표현하지 않는다.
- 인물 명언은 원문·출처·번역·사용 조건을 확인한 문구만 포함한다. AI가 유명인 발언을 생성하지 않는다. 명언 CMS·무한 피드·별도 구독형 코치는 첫 버전에서 제외한다.

## 프론트엔드와 백엔드 경계·개발 순서

[이미 전달한 요청서](../api/API_PERSONAL_SYSTEMS_REQUEST.md)는 합의 전 초안이며 이번 IA 제안 때문에 조용히 변경하지 않는다. 추가 API가 생기면 별도 변경 요청으로 전달한다.

| 순서            | 프론트엔드 작업                                                                               | 백엔드 의존·완료 조건                                                                        |
| --------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 1. 구조 비교    | A/B/C를 동일 데이터의 390×844 시각안으로 비교. 오늘·계획·돌아보기·달력 진입 및 3번 sheet 연결 | API 불필요. 사용자 선택 후 구현                                                              |
| 2. 탐색·기초 UI | 선택된 탭·header·작성 진입·아이콘·용어. 기존 목적지·route 보존                                | 기존 API로 가능. Android/iOS/Web 실제 화면 감사                                              |
| 3. 기록 정합성  | 빠른 입력의 선택 유형·실제 결과·성공 안내 일치, 날짜 갱신·복귀 보완                           | mock/real 비교. 타입 강제 정책에 계약 변경 필요 시 추가 요청                                 |
| 4. 핵심 시스템  | 목표→여러 반복 계획→기본/최소 실천+일회성 노력→목표 여정. 상세는 목표 여정 명세 기준          | 시스템·회차·실천·휴식·취소·버전/시간대·게스트 계약 확정 필요                                 |

| 6. AI·다독임    | AI 초안과 직접 입력, 근거 요약과 정형 fallback. 정적 문구·덜 보기                             | AI endpoint/입력 범위/오류 정책은 서버. 정적 문구·빈도 로컬 구현은 백엔드 불필요             |

돌아보기 탭은 초기에는 기존 완료 기록을 실제 내용으로 제공할 수 있다. 준비되지 않은 주간 증거를 가짜 수치·예시 칭찬으로 채우지 않는다. 새 시스템 entry는 사용 가능한 단계에서 노출한다. 시스템 생성·주간 회고 시각 방향은 별도 검토가 남아 있다.

## 선택한 구조에서 확인할 사용자 과제

실제 사용자 5–8명 정도의 짧은 탐색/클릭 시안 검토부터 시작한다. 아래는 목표 기준이며 아직 얻은 결과가 아니다.

| 과제                          | 확인할 것                                                                              |
| ----------------------------- | -------------------------------------------------------------------------------------- |
| 다음 주 수요일의 일정 찾기    | 달력을 첫 선택에서 찾는가, Today에서 한 번에 열리는가; B가 C보다 혼동되면 달력 탭 유지 |
| 날짜 없는 바람 보관하기       | 날짜 입력이나 시스템 생성 없이 저장할 수 있음을 이해하는가                             |
| 오늘은 최소 행동으로 시작하기 | 목록에서 다음 행동을 알고 3번 sheet에서 압박 없이 선택하는가                           |
| 이번 주 실제 한 일 확인하기   | 완료 숫자와 자기 기록을 찾고, 요약의 근거를 구별하는가                                 |
| 며칠 뒤 돌아와 이어가기       | 밀린 회차를 모두 처리해야 한다고 오해하지 않는가                                       |
| 공유 공간·설정 찾기           | 기존 사용자에게 필요한 목적지가 이동 후에도 발견되는가                                 |

첫 선택·완료 여부·망설인 지점·추가 탭 수와 사용자 설명을 기록한다. 작은 표본의 선호를 유지율 상승으로 주장하지 않는다. 이후 실제 사용에서 회차 확인·주간 기록 열람·복귀 경로를 평가하되 개인 메모 원문을 분석 이벤트에 넣지 않는다.

## 이번 작업의 완료 범위

실제 화면 감사, 공개 레퍼런스 조사, 페이지별 존치/이동안, 세 가지 탐색 구조 비교, 추천안과 개발 의존성을 문서화했다. 앱 코드·백엔드 요청 계약은 변경하지 않았다. 세 보드 비교와 사용자 조합 방향 선택을 마쳤다. 다음 완결된 작업은 **선택한 조합과 일상 반복 행동을 반영한 시안 검토**이며, 기존 실행 sheet 선택은 다시 묻지 않는다.
