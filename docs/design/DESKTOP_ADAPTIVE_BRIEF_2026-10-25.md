# PC 적응형 배치 검토 범위

2026-10-25 · 세로 목록 구조 선택 · 모바일 우선/PC UI 구현 전

## 사용자 목적과 범위

PC에서도 목표와 할 일을 편하게 관리하고, 목록을 잃지 않은 채 상세를 읽고 수정한다. 사용자는 PC 활용 방향과 접근 권한 확인을 먼저 진행하는 순서에 동의했다. 보안 검증은 [STG 결과/운영 대기](../qa/task-authorization-2026-10-25/README.md)로 별도 관리한다. PC 탐색/상세 구조는 의미 있는 새 선택지이므로 시각3안을 비교하고 선택 후 코드에 반영한다.

## 현재 기준과 유지할 것

현재 `Screen`, `PlannerHeader`, 하단 탭, `DetailSheet`의 공통 최대 너비는720이다. 본문 여백은360 미만16, 그 외20이다. 이 값은 모바일 중심 한 열을 유지하기 위한 현재 공통값이며 PC 최적값으로 검증한 수치는 아니다. 같은 창 너비에 따라 전환하며 OS/기종 이름으로 PC를 판별하지 않는다.

유지: 모바일 [오늘 원본](./goal-lanes-correction-2026-10-21/reference.png), [계획 목표 탭](./plan-navigation-2026-10-15/05-goal-tabs-polished.png), [상세 선택05](./task-detail-options-2026-10-24/05-context-panel-aligned.png), 흰 바탕/파랑·세이지 목표 색/세로 레일/원형 체크/짧은 동기부여 문구. 모바일 하단 순서 오늘·달력·계획·돌아보기, Drawer 보조 역할은 유지한다. 오늘에 큰 제목/상시 날짜/주 달력/목표 퍼센트/항목별 카드·구분선/실적 점수를 추가하지 않는다.

## 검토할 구조

공통 방향은 전체 작업 공간 활용, 왼쪽 주요 탐색, 읽기 너비를 유지한 중앙 목록, 선택 시 상세를옆에서 읽는 것이다. 폭을 늘려 제목과 버튼 사이만 벌어지는 안은 지양한다. 목표별 Task를 독립 카드/임의 대시보드로 바꾸지 않는다.

시각 비교의 차이는 탐색과 상세를 두는 방식이다. 접을 수 있는 고정 사이드바와 붙어 있는 우측 상세, 얇은 탐색 rail과 더 넓은 작업 영역, 목표 탐색을 강화한 두 열 작업 공간을 비교한다. 생성 결과와 파일을 연결했고, 사용자는01의 모바일과 이어지는 세로 목록 구조에 동의했다. PC 구현보다 모바일 사용성 보완을 우선한다.1440×1024를 비교 기준으로 하고 모바일 이미지는 시각 언어의 참조로 첨부한다. 생성 이미지는 실제 앱 캡처/작동하는 prototype가 아니다.

오늘은 실행, 계획은 목표/반복/일회성 항목 구성, 달력은 날짜별 탐색, 돌아보기는 실제 기록의 역할을 유지한다. 우측 상세는 항목 선택 때만 표시하며 닫기/뒤로가기/키보드 초점/직접 URL을 함께 설계한다. PC의 순서 편집도 드래그 외 키보드 조작/취소를 제공한다. 지원할 화면마다 별도 앱이나 API를 만들지 않고 공통 데이터/컴포넌트를 재사용한다.

## 검토 기준·자료

Product Design get-context/ideate, 저장소 구현 가이드와 기본 시각 검사. 기존 앱/선택 원본을 직접 확인하고 참조 이미지를 붙여 생성한다. user-context preflight의 저장 context 유무는 생성 기록에 적는다. Figma/외부 앱 직접 조작은 하지 않는다.

외부 공식 자료는10월25일 대화에서 확인한 [Todoist sidebar](https://www.todoist.com/help/todoist/features/customize-the-sidebar-and-navigation-menu-in-todoist-S9JLTYqZV)와 [Android list-detail](https://developer.android.com/develop/ui/compose/layouts/adaptive/list-detail)을 재사용한다. 전자는 PC 사이드바와 모바일 탐색의 구분, 후자는 넓은 창의 목록·상세 동시 표시/좁은 창의 단일 pane 전환 근거다. Dooit에서의 추천 배치는 설계 판단이며 해당 앱의 사용성 테스트 결과를 대신하지 않는다. 새 Kotlin 라이브러리나 외부 디자인 체계를 도입하지 않는다.

확인할 사항: 충분한 읽기 너비/아이콘·행 중심·44px 조작 영역/과도한 공백, 선택/완료 상태, 목표 이름과 할 일 제목의 줄바꿈, 키보드/초점/뒤로가기/미저장 보호, 창 축소 시 선택과 입력 보존, 달력·돌아보기로 이동할 때 탐색의 일관성. 두 열/세 열 전환점은 시각 선택과 실제 구현 검증에서 정하며 현재840 기준을 전역 정답으로 확정하지 않는다.

## 후속 완료 조건

1. 정확한 시각3안과 표시 순서/파일을 저장하고 선택/보정을 받는다.
2. 선택한 PC 탐색 뼈대→오늘/상세→계획→달력/돌아보기 순서로 독립 구현한다.
3. 같은 데이터의 mobile320/390/430와 desktop1024/1440 실제 캡처, 새 좌표 검사, 키보드/창 크기 전환/직접 URL/작성 보호를 확인한다.
4. 현재 선택된 모바일 시안은 별도 동의 없이 바꾸지 않는다. 구현·실제 Web 감사·native/운영 API 미확인을 분리한다.

이번에는 PC 레이아웃 코드를 바꾸지 않았다. [실제 표시 순서에 연결한 시각3안과 검토](./desktop-adaptive-2026-10-25/README.md)를 생성했고01의 세로 목록 구조를 선택했다. 제목 앞 전체 완료 체크는 사용자 동의에 따라 오늘과 같은24px 시각/44px 조작 영역으로 유지한다. 생성 이미지의 큰 원/세부 수치는 그대로 옮기지 않는다.
