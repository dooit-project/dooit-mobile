## 화면과 저장

- `GoalPlanList`: Goal별 실제 계획 API를 읽고 회차를 매일 나열하지 않는다. 이름·선택 요일·멈춤 상태를 표시하고 행 전체로 수정한다. 보관 계획은 개수와 펼침으로 조회하며 보관된 Goal/Plan은 편집하지 않는다. 항목이 없다는 별도 일정/습관 안내는 만들지 않았다.
- `GoalPlanForm`: 반복할 일, 요일, 시작일, 시작 상황(선택), 평소 행동과 힘든 날의 작은 행동을 입력한다. 분량·예상 시간·다음 행동은 선택 입력으로 접는다. 기본은 눈에 보이는 시작일과 매일 선택이며 사용자 저장 전에는 만들지 않는다. AI 호출은 없다.
- 수정 시 시작일과 적용일은 별개다. 기존 시작일·시간대·알림 시각·수량/시간을 보존하고 적용일만 기본 오늘로 제안한다. 사용자 수정 가능하다. 알림 예약 UI는 아직 연결하지 않았으므로 새 알림 설정은 노출하지 않는다. 기존 알림 값이 있으면 유지됨을 표시한다.
- 본문 `반복 계획 추가`에서 같은 위치의 작성 폼을 연다. 일회성 목록 계약이 확인되면 단일 `항목 추가`에 종류 선택을 통합할 예정이다. 현재 일회성 버튼을 비활성 상태로 붙이거나 반복을 일반 Task처럼 저장하지 않는다.
- 수정/생성·상태 변경을 분리한다. 상태 확인에는 입력 중 내용은 저장하지 않는다는 안내가 있다. 멈춤/보관은 앞으로의 연결 Task를 멈추고 지난 기록을 보존하며, 보관 후 수정/활성화가 불가능함을 알린다.

## 실패·권한·접근성

작성 중 목표 탭·전체 목록·목표 관리 전환을 잠그고 폼 취소로 빠져나온다. 저장 중 중복 요청과 취소를 막는다. 날짜/필수 행동/요일/예상 시간 오류와 API 실패는 값을 유지한다. 편집 snapshot을 잡고 조회된 version/상태가 달라지거나 원본이 없어지면 값을 남긴 채 저장/상태 변경을 막는다. 서버에 예상 version을 조건부로 보내는 계약은 없으므로 마지막 조회 뒤 동시 변경까지 원자적으로 막는 것은 아니다.

목표 ID를 수정 요청에 명시해 생략으로 독립 계획이 되지 않도록 한다. 계정 전환 후 늦게 도착한 응답은 새 계정 캐시에 쓰지 않는다. 성공 시 목록/상세와 회차·여정·Task·일일 계획을 갱신한다. 목록 오류 시 재시도와 남아 있는 데이터를 제공한다. 실제 저장 결과를 받지 못한 생성의 중복 방지는 기존 Goal과 마찬가지로 서버 멱등성 후속이다.

입력 48·행 64 기준, 요일 선택 상태·펼침 상태·오류 텍스트를 제공하고 기존 버튼을 재사용한다. 긴 이름은 줄바꿈한다. 실제 작은 화면/키보드/글자 확대/보조 기술/초점 이동은 확인하지 않았다.

## 일회성 목록 계약과 다음 작업

확인한 로컬 GoalTask controller는 생성/연결/해제를 제공하지만 목표별 Task GET은 없고 TaskSearch 요청에도 linkedGoalId 필터가 없다. 응답 linkedGoalId만으로 일부 날짜의 Task를 모아 전체 목표 목록처럼 표시하지 않는다. [백엔드 요청서 G-07](../api/API_GOAL_JOURNEY_CHANGE_REQUEST.md)에 필터 추가 요구를 기록했다. 미전달·미합의이며 운영 API를 호출해 부재를 검증한 결과는 아니다.

새 Goal의 일회성 Task 작성·목록과 혼합 순서 편집은 F2b-2다. 반복 계획의 오늘 회차 실행은 확정된 API로 독립 진행 가능하므로 다음 구현 우선순위는 F3a다. 현재 작성된 반복 계획을 오늘 화면이 자동으로 조회/구체화하거나 새 native 알림을 예약하는 단계는 아니다.

요청 변환의 Goal 유지·시간대/알림 정밀도/수량 보존·적용일·선택값 초기화와 잘못된 날짜/요일/시간 차단 사례를 작성했다. 테스트·`npm run validate`·실제 화면 감사·운영 API 호출은 사용자 요청대로 실행하지 않았다. 코드/포맷 반영을 검증 통과로 기록하지 않는다.
