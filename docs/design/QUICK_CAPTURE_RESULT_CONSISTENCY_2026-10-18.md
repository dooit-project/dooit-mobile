# 빠른 기록: 실제 저장 결과와 안내 일치

2026-10-18 · `6b7ac90` 커밋 · 미검증

계정 화면 정리는 `2cbbb82`로 커밋하고 `origin/main`에 푸시했다. 이어서 저장 원본에 맞는 빠른 기록 안내와 제출/이동 상태를 수정하고 저장 유형 정책은 별도 백엔드 요청으로 분리해 `6b7ac90`으로 커밋했다. U3 전체가 완료된 것은 아니다.

## 코드에서 확인한 원인과 범위

- 현재 오늘의 추가 메뉴는 일정·아이디어를 `/tasks/new`로, 할 일을 한 줄 `QuickCapture`로 보낸다. 세 유형 모두 별도 폼을 사용한다는 초기 설명은 잘못이어서 대화에서 정정했다.
- quick-capture 요청에는 사용자가 고른 유형 필드가 없다. mock은 파싱 성공 시 SCHEDULE/TODAY를 만든다. real API의 저장 정책은 새로 확인하지 않았다.
- 기존 결과 안내는 TODAY 상태만 보면 `오늘 할 일`이라고 표현했다. 나머지 결과는 parser metadata를 사용해 실제 task의 유형·날짜·반복 저장 여부와 어긋날 수 있었다.
- 현재 응답의 `task.type/status/plannedDate/startAt/allDay/recurrence...`를 실제 저장 원본으로 사용한다. TODAY 상태가 날짜의 오늘을 뜻한다고 가정하지 않는다.

## 이번 코드 변경

- 완료 상태는 완료 기록, 기록함 상태는 실제 유형(할 일·일정·아이디어)과 기록함 위치를 안내한다. 파싱 성공/실패만 보고 위치를 추정하지 않는다.
- 할 일은 실제 plannedDate가 현재 앱 날짜와 일치할 때만 `오늘 할 일`로 표현한다. 다른 날짜는 연도를 포함한 날짜, 날짜가 없으면 유형만 안내한다.
- 일정은 실제 startAt을 우선하고, 없으면 유효한 plannedDate를 사용한다. 실제 allDay·시각을 구분하며 원본에 저장된 반복 규칙만 표시한다. parsedDate/Time/Type/Recurrence 값은 성공 안내에 사용하지 않는다.
- 아이디어는 현재 오늘 실행 목록이 제외하는 유형이므로 임의로 오늘 목록에 들어갔다고 말하지 않는다.
- 생성/오늘 이동 중에는 입력·닫기·추가 제출을 잠그고, 같은 프레임의 중복 요청도 ref로 차단한다. 이동 결과는 같은 Task ID의 현재 결과에만 적용한다. 기존 원본 저장/이동 API·캐시 갱신·내용 확인 경로는 유지한다.
- 생성 실패 시 원문 입력을 유지하는 기존 흐름을 보존한다. 서버의 timeout 후 중복 생성/멱등성 정책은 이번 UI 잠금만으로 보장하지 않는다.
- 기존 결과 안내 회귀 사례를 저장 원본이 포함된 fixture로 갱신하고 파서/원본 충돌·미래 계획·종일·저장되지 않은 반복의 사례를 추가했다. 테스트 실행은 사용자 요청대로 보류했다.

## 구현 전 검토와 한계

대상은 한 줄 기록의 저장 결과를 정확히 이해하는 것이다. 기존 [UI-06 감사 기록](../audits/ui-structure-2026-10-12/README.md), 현재 Today 진입 코드·결과 helper·요청/응답 타입·mock parser·이동 mutation을 읽고 기존 입력창/결과 notice 안의 문구와 상태를 수정했다. 신규 화면·내비게이션 구조·버튼 배치를 만들지 않으므로 새 시각안 세 개는 만들지 않았다. Product Design의 원본 근거·상태 일치 기준과 저장소 기본 검토 정책을 재사용했다. 이번에 Figma·외부 앱·새 생성 이미지를 사용하지 않았다.

영향 플랫폼은 Android·iOS·Web이다. 실제 브라우저·기기·mock/real API 재현, `npm run validate`와 테스트 실행은 사용자 요청으로 보류했다. 코드 확인과 테스트 파일 갱신을 통과로 기록하지 않는다. 기존 날짜 없는 할 일/일정 자동 분류 정책·날짜 해석 실패 시 처리·자정 이후 열린 화면의 기준일 갱신은 별도 확인이 남아 있다.

## 남은 일
