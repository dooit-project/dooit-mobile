# TaskForm 첫 오류 위치와 수정 흐름

2026-10-26 · 기준 `34d470c` · 구현 전 검토

- 이번 단위: 기본 TaskForm에서 잘못된 입력의 위치·수정 방법 안내와 첫 오류 초점.
- 원본: 사용자 선택 [속성 행01](../../design/task-form-density-2026-10-26/01-property-rows.png)과 이번 [실제 기본 화면](./01-before-normal-390.jpg)/[날짜 오류](./02-before-date-error-390.jpg)를 직접 확인했다.
- 유지: 기본 입력/두 속성 행/추가 정보·저장 위치, 제목이 비어 있을 때 저장 비활성, 기존 단위·범위/저장·취소/dirty·중앙 확인과 API 계약.
- 변경: 필드 아래 구체적인 오류 문구·invalid 표시/설명 연결, 화면 순서상 첫 오류 초점, 숨겨진 예상 시간 오류의 추가 정보 자동 펼침. 오류가 없는 화면은 바꾸지 않는다.
- 범위 밖: 새 오류 요약 화면/확인창·버튼 추가, 날짜 picker/R4, 전체 공통 폼 교체, 서버 오류를 특정 필드 오류로 추정하기, 백엔드/의존성 변경.
- 완료 조건: 같은390 정상/오류 전후 비교,320/430·짧은 화면·여러 오류/반복 제출·복구·새 작성/편집·접힌 입력, 실제 좌표/console와 validate.

Product Design audit/design-qa와 저장소 구현 가이드/기본 시각 검사를 적용한다. 저장 context는 없으며 Figma/새 이미지 생성은 사용하지 않는다. 선택한 기존 구조의 오류 상태 보정이므로 새 정보 구조3안을 다시 선택하지 않는다.

## 구현 전 실제 관찰

Chrome 확장 browser1의 기존 연결을 이어 localhost8082/mock goal-lanes/light/390×844에서 새 캡처했다. IAB 접근 실패 후 유지하던 같은 환경이며 browser surface/local Playwright로 전환하지 않았다.

1. 기본 수정 — 두 속성 행/기본 필드 위계 유지. 오류 없는 화면은 이 기준을 유지한다.
2. 날짜를2026-02-30으로 입력하고 저장 — 오류는 폼 맨 아래에 표시되고 날짜에는 invalid 표시가 없다. 초점은 수정 완료에 남고, 날짜와 설명이 떨어져 있다. 입력은 보존되지만 오류 위치를 다시 찾아야 하므로 수정 필요다.

## 외부 기준과 판단

2026-10-26 직접 읽은 [W3C 오류 식별](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)은 잘못된 항목과 문제를 텍스트로 식별하도록 설명한다. [WAI 폼 알림](https://www.w3.org/WAI/tutorials/forms/notifications/)의 필드 근처 안내·수정 방법·프로그램상 설명 연결을 참고한다. 오류 목록/추가 dialog가 필수라는 뜻은 아니므로 Dooit의 짧은 폼에서는 기존 한 오류 안내를 해당 필드 아래로 옮기고 첫 오류에 초점을 둔다. 자동 검사가 스크린 리더/실기기 적합성을 보증하지 않는다.

추가로 같은 날 [GOV.UK Error message](https://design-system.service.gov.uk/components/error-message/)의 입력값 보존·오류와 필드 연결·라벨을 포함하는 구체적인 수정 안내를 참고했다. GOV.UK가 안내하는 상단 오류 요약 전체를 복제하지 않고, 기존 첫 오류 방식의 짧은 Dooit 폼에 필드별 안내를 적용했다. 공식 서비스 디자인 문서 참고이며 경쟁 앱을 로그인·직접 조작한 검토는 아니다.

## 구현과 같은 조건의 비교

공통 TextField에 선택적 오류 문구/ID를 전달해 기존1px 경계와 초점 표현을 유지하면서 Web `aria-describedby`와 native 오류 hint를 연결했다. 표시 문구는 기존 AppText caption13/18·danger token이다. 폼 아래의 단일 문자열 대신 오류 대상 필드를 함께 저장하고 해당 위치에 한 문구만 표시한다. 날짜/시작/종료를 식별하는 정규화 결과에 오류 필드를 추가했으며 API 요청 값/성공 결과는 바꾸지 않았다.

검사 순서는 제목→날짜/시작/종료→반복 guard→예상 시간으로 화면 순서를 따른다. 오류가 있는 필드/관련 입력을 수정하면 그 안내를 해제하되, 무관한 설명 입력만 바꿔 오류가 사라지지는 않는다. 종일/유형 전환은 숨겨진 오류를 해제한다. 예상 시간 오류는 접힌 추가 정보를 펼친 뒤 commit 이후 해당 TextInput을 focus한다. 반복 설정의 별도 편집/초안·Back 흐름은 유지한다.

[전후 전체/부분 비교판](./09-before-after-comparison.jpg)은 이번 실제 캡처를 HTML에 함께 놓고 직접 확인한 것이다. 정상은 같은390×844·제목/날짜/시간/반복 없음/추가 정보 접힘이며 글자 커서 위치 외 배치·크기·색·조작 수가 같다. 오류도 같은390×844·2026-02-30/나머지 값으로 비교했다. 이전은 저장에 초점이 남고 오류가 맨 아래였고, 이후는 해당 입력의 red 경계·바로 아래 문구·입력 초점으로 바뀌었다. 초점 이동에 따라 스크롤 위치가 달라졌으므로 위쪽 제목이나 날짜의 절대 y 차이를 레이아웃 변화로 판단하지 않는다. 부분 비교는 이전 하단 y660/수정 후 날짜 y285 부근을 각각 잘라 오류 위치를 보여준다. 앱 UI 생성/조작 합성이 아니며 임시 HTML은 캡처 후 제거했다.

필수 다섯 면을 확인했다. 공통 글꼴/16·14·13 크기/행간 유지, 정상 간격/폭·높이 유지, 기존 danger/primary/중립 token 유지, 새 이미지/아이콘 자산 없음, 기존 오류 문구/기본 입력/두 속성 행 문구와 값 보존이다. 시작/종료 오류는 반쪽 칸의 끝에서 한 글자씩 끊겨 보이는 문제를 피하려고 **시간 행 바로 아래 전체 폭**으로 표시하며 문구에 어느 시간인지 명시한다. 입력 자체의 오류 경계와 ID 연결은 해당 칸에만 적용한다.

## 실제 단계와 수정 이력

1. **날짜/반복 제출 — 수정 후 양호:** [날짜 오류390](./04-after-date-error-390.jpg)에서 red 경계·문구·초점이 유지된다. [실제 DOM](./date-error-390.json)은 활성 일정 날짜, invalid=true, 실제 오류 ID/문구 연결, 입력과 오류 모두 viewport 안임을 보여준다. 같은 저장을 다시 눌러도 같은 필드로 복귀했다.
2. **복수 오류 — 양호:** 시작25:00/종료13:00/접힌 예상 시간1을 함께 둔 뒤 저장했다. 시작→수정→종료→수정→예상 시간으로 이동했고, 각 단계에서 다른 입력은 유지했다. [실제 순서/설명 보존](./validation-flow.json).
3. **좁고 넓은 화면 — 수정 후 양호:** [320](./05-end-error-320.jpg)/[430](./06-end-error-430.jpg)에서 종료 오류를 해당 red 입력과 전체 시간 행 아래 문구로 읽을 수 있다. 처음 반쪽 칸 아래에서는 문장이 잘게 끊겨, 전체 행 폭으로 보정한 뒤 새로 촬영했다.
4. **접힌 입력/짧은 화면 — 양호:** [390×568](./07-duration-error-short-390.jpg)에서 예상 시간을 펼치고 focus한다. 실제 입력 y305–349·문구 y357–375로 모두 보이며 설명 ‘접수 준비물 확인’을 보존한다.25로 수정하면 invalid/오류 설명이 해제된다. 부모 취소→기존 중앙 버리기로 원래 상세/수정 초점에 복귀했다.
5. **새 작성 — 양호:** [새 일정 오류390](./08-new-schedule-error-390.jpg)에서도 시작25:00을 안내하고 활성 초점을 유지한다. 제목 ‘영단어 복습’은 보존했다. 제목이 비어 있으면 저장 비활성인 기존 규칙도 유지한다. 빈 제목 guard는 단위 회귀 범위이며 비활성 버튼을 실제로 눌러 오류를 보인 검증은 아니다.

초기 구현에서 P2 초점 소실을 발견했다. React Native Web ScrollView의 `on-drag` 구현(`node_modules/react-native-web/src/exports/ScrollView/index.js`)은 프로그램으로 발생한 scroll에도 dismissKeyboard를 호출해, 오류 focus 직후 blur가 발생했다. 공통 Screen/DetailSheet에서 **Web만 none**, native는 기존 on-drag로 두었다. 이후 새 작성·기존 수정에서 스크롤과 캡처 후에도 활성 입력이 유지됨을 실제 DOM으로 재확인했다. 이 보정은 공통 Web 스크롤 화면에 영향을 주며 native 키보드 정책을 변경한 것은 아니다. 기본 시각 검사에도 스크롤 이후 오류 초점 유지 항목을 추가했다.

## 검사와 한계
