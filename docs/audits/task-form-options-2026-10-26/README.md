# TaskForm 알림·반복 선택 정돈

> 이 문서는 이전 미커밋 inline 표현 실험의 이력이다. 이후 사용자가 선택한 [속성 행 구현/실제 감사](../task-form-properties-2026-10-26/README.md)가 현재 기준이며, 이 문서의 ChoiceChips 실험은 최종 코드에서 제거했다.

> **재평가: 전체 UX는 수정 필요.** 사용자의 버튼 과다 지적 후 [새 실제 재감사](../task-form-density-review-2026-10-26/README.md)에서7/5/3개 선택의 동시 노출 문제가 남아 있음을 확인했다. 아래 passed는 선택 상태/키보드·표현 보정의 제한된 검사 이력이며 전체 화면의 디자인 승인이나 밀도 해결을 뜻하지 않는다. 다음 작업은 첫 오류 초점보다 노출 구조 선택/개선을 우선한다.

Product Design index/audit/design-qa와 저장소 구현 가이드/기본 시각 검사를 적용했다. user-context preflight는 저장 항목 없음이다. 기존 코드 대상과 inline 선택을 보정하는 범위로 새 정보 구조를 만들지 않는다. 별도 요약/선택 화면을 도입한다면 시각3안과 선택을 별도로 진행한다.

## 구현 전 실제 관찰과 외부 자료

Chrome 확장 browser1의 기존 연결을 이어 localhost8082 mock goal-lanes/light/390×844에서 새 캡처했다. 초기 screenshot이 DOM viewport와 달리 축소되어 같은 브라우저에서 override reset→390×844 재설정 후 다시 촬영했다. 새 browser/local Playwright로 전환하지 않았다.

알림7/반복5/직접 단위3이 각각 경계가 있고 선택 면은 blue/green으로 다르다. 유형 외15개 radio의 실제 Web DOM에는 aria-checked가 없고 모두 tabindex0이다. 직접 반복의 단위는 세 별도 박스로 표시된다. 타입처럼 공통 동작을 재사용해 의미/초점과 시각 규칙을 함께 정돈한다.

2026-10-26 공식 자료를 새로 직접 읽었다.

- [Microsoft To Do 날짜·알림·반복](https://support.microsoft.com/en-gb/todo/add-due-dates-and-reminders-in-microsoft-to-do?nochrome=true): 알림과 반복을 다른 속성으로 구분하고 일/주/월 등 일반 선택과 직접 설정을 제공한다. Dooit에서도 두 속성을 합치거나 선택지를 줄이지 않는다.
- [Todoist 반복 날짜](https://www.todoist.com/help/todoist/features/introduction-to-recurring-dates-YUYVJJAV): 자주 쓰는 반복과 custom 설정의 역할을 참고한다. Dooit에 자연어 입력이나 완료일 기준 반복을 새로 추가하지 않는다.
- [WAI-ARIA Radio Group](https://www.w3.org/WAI/ARIA/apg/patterns/radio/): 한 그룹 한 선택/이름/checked, 선택 항목으로 Tab 진입, 방향키 순환·Space 선택. 줄바꿈한 chip도 같은 단일 선택 규칙을 적용한다.

위는 공식 사용 자료의 패턴 비교이며 경쟁 앱을 로그인해 직접 사용하거나 최신 앱의 픽셀을 비교한 것은 아니다. 새 Figma/이미지 생성도 사용하지 않는다. 선택된 속성만 강조하는 색·반경/밀도는 Dooit 공통 token에 맞춘 설계 판단이다.

## 구현 결과와 전후 비교

기존 SegmentedControl의 단일 선택 로직을 내부 공통 그룹으로 분리하고 ChoiceChips가 같은 checked/disabled/키보드/초점 동작을 쓰도록 했다. TaskForm의 알림7·반복5는 줄바꿈 chip, 직접 반복의 일/주/개월은 기존 유형과 같은 segmented 표현을 사용한다. 다른 화면의 선택 UI는 바꾸지 않았다.

[전후 전체/부분 비교판](./08-before-after.jpg)에서 이번 원본과 실제 수정 후를 함께 직접 확인했다. 같은390×844/같은 선택(시작 시각·직접 설정·주·간격2)이며, 두 캡처의 스크롤 위치가 달라 알림 라벨이44px 차이 난다. 이를 폼 이동으로 잘못 판정하지 않도록 아래 부분 비교는 원본 y100/수정 후 y144를 기준으로 라벨을 맞췄다. 실제 캡처를 HTML에서 표시한 QA 비교판이고 앱 화면을 생성/합성한 것이 아니다. 임시 HTML은 제거했다.

- [수정 후390](./02-after-390.jpg): 비선택 항목의 반복된 외곽선을 없애고 surfaceMuted 배경/중립 글자로 표현한다. 선택된 chip만 primarySoft/primary 경계·글자/semibold를 쓴다. 기존 blue/green 혼용을 해소했다. 글자13/18→14/20, 좌우 여백12→8, 조작 높이44는 유지했다. pill 반경999→공통 control 반경10이다.
- 직접 반복의 단위 세 항목은52px 그룹 안에 각44px 조작 영역을 두었다. 기존44px 행보다8px 커진 것은 그룹 안쪽4px씩의 의도한 여백이다. 간격 입력/설명/예상 시간/카테고리와 기본 폼의 값·순서·너비/위계는 유지한다.
- [320](./04-after-320.jpg)·[430](./05-after-430.jpg): 선택지는 화면에 맞춰 줄바꿈하고 단일 선택/조작 영역을 유지한다. 캡처는 해당 스크롤 위치의 실제 viewport이므로 위쪽 일부가 스크롤되어 가려질 수 있다. 알림/반복 선택지를 삭제하거나 새 화면으로 숨기지 않았다.
- 폰트/간격/색 token/이미지 품질/문구를 각각 검토했다. chip의 medium/semibold와14/20은 기존 AppText, 색·반경·간격은 공통 token이다. 새 이미지/아이콘 자산은 없다. 키보드 초점은 파란2px 외곽선으로 선택 경계와 구분한다. 마우스/터치 상태를 키보드 초점 제거로 해결하지 않는다.
- 초기390×184 축소 캡처와 개발 갱신 표시가 남은 기본 캡처는 같은 Chrome viewport를 reset/재설정해 재촬영했다. 최종 기본/종일390은390×844,320은320×844,430은430×932,짧은 화면은390×568이다.
