## 구현 전 확인

- [기존 목표 390](./01-health-before-390.jpg), [320](./02-health-before-320.jpg): 건강 목표 본문/밑줄은 선택됐지만 Web aria-selected가 없고 AX는 선택 false로 읽힌다.
- [새 긴 목표 생성 직후 320](./03-created-before-320.jpg): 로컬 mock에서 ‘나만의 작은 서비스를 꾸준히 만들어서 출시하기’를 UI로 생성했다. 새 탭 x=195.24, 오른쪽404.24/폭209로 화면 밖이며 전체 목표 버튼 영역과 겹치는 위치에 가려진다. 선택 aria 속성도 없다.
- 현재 코드는 선택 효과가 탭 onLayout 전에 실행되면 위치를 모르는 상태로 종료하고, 탭 onLayout은 위치만 기록해 다시 노출하지 않는다. 탭 폭도 스크롤 표시 영역보다 커질 수 있다. 새 목표는 mock 메모리 데이터이며 검증 후 기본 fixture/기존 선택으로 되돌린다.

## 구현 판단

`GoalTabs`가 표시 폭·내용 폭·각 탭의 x/width를 함께 측정하고, 선택 변경/늦은 탭 layout/내용 크기/화면 폭 변경 후 필요한 만큼만 스크롤한다. 긴 이름은 표시 영역 이내의 한 줄 말줄임이며 전체 이름은 접근성 이름과 본문에서 유지한다. Web에서 layout 폭 반올림 때문에 탭 폭에 1px 여유를 두었다. 실측 경계에는 1px 미만의 소수점 반올림 차이가 남으며 픽셀 완전 일치를 주장하지 않는다.

[W3C APG Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)를 2026-10-23 직접 읽고 탭 그룹/단일 선택/본문 연결·키보드 이동에 적용했다. 본문 조회가 있을 수 있어 화살표/Home/End는 초점만 옮기는 수동 활성화로 구현하고 Enter/Space로 선택한다. 선택 탭만 일반 Tab 진입점이며 키보드 초점은 별도 outline으로 표시한다. 원래 가로 탭 구조를 바꾸거나 전체 접근성 적합 판정을 하는 것은 아니다.

각 캡처를 저장하고 직접 열어 비교했다. 생성 검증의 자동 fill 값이 유지되지 않아 실제 DOM/AX 값이 빈 상태임을 확인했고, 동일 Chrome의 기본 입력으로 이름을 넣은 뒤 생성 성공을 확인했다. 별도 browser surface/Playwright CLI 전환이나 DOM 상태 주입은 없다. 수정 직후 Space가 기본 Pressable tab 역할에서 활성화되지 않는 점을 실제로 발견해 명시 처리한 뒤 selected=true를 재확인했다. RN 타입에서 tabpanel은 accessibilityRole 대신 지원되는 role 속성으로 수정하고 필수 검사를 마쳤다.

임시 목표 두 개는 로컬 mock 메모리에서만 생성했고 reload로 기본 두 목표에 복귀했다. 마지막 선택 복원 확인 후 원래 토익 목표로 돌리고 viewport override를 해제했다. 선택/색상 저장은 기존 UI 계약만 사용하며 저장 형식을 바꾸지 않았다. 최종 tab error 로그 0.

## 검증과 경계

- `npm run validate` 통과: 116 suites / 597 tests, STG 1개 제외. 늦은 측정·현재 노출 유지·양 끝/폭 변경·숨김/미측정과 키보드 경계에 대한 동작 테스트 5개를 추가했다. 스타일 수치 복제 테스트가 아니다.
- Android/iOS/Web 공통 영향. 실제 확인은 Web light 320/390/430이며 native·fontScale1.5·dark·VoiceOver/TalkBack·실제 서버·조회 실패/계정 전환은 미확인이다. 실제 UI 순서 편집 후 재노출은 별도 확인하지 않았다.
- 탭 전체가 보이는 것과 긴 목표 이름 전체를 한 줄에 표시하는 것은 다르다. 긴 이름은 의도적으로 말줄임하고 본문/전체 목표/접근성 이름에서 확인한다. 나머지 이웃 탭이 일부 잘려 보이는 기존 가로 스크롤 구조는 유지한다.
- 별도 기존 D-Day 관리 페이지는 이번 GoalTabs로 교체하지 않았다. 상세 정보 축·폼 오류 복귀·Goal 회차 연결·UX-14 캐시도 미완료다.
