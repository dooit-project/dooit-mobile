# 하단 탭 높이와 시스템 영역 분리

Last updated: 2026-09-14

## 구현 전 검토

- 기준 commit: `fbf849e`. 사용자가 실제 앱에서 하단 탭이 작고 홈 제스처 영역에 붙어 보인다고 보고했다.
- 목표: 오늘·달력·더보기의 기존 구조를 유지하면서 터치 영역과 아이콘·글자 여백을 키우고 시스템 하단 영역을 따로 확보한다. 기존 패턴의 작은 크기 조정으로 신규 화면·정보 구조 시각안 비교는 적용하지 않는다.
- 현재 Web 캡처: [01-before-390.png](./01-before-390.png). Web 높이는 64px, native는 navigator 기본 49pt + inset에 의존한다. 실제 기기의 겹침은 아직 직접 재현하지 않았다.
- 참고: [네이버 앱 공개 화면(2023)](https://zdnet.co.kr/view/?no=20231031102101), [배민 홈·주문 화면 분석](https://brunch.co.kr/@3o3design/8)의 공개 이미지를 직접 확인했다. 아이콘 아래 짧은 라벨, 균등한 탭 너비, 시스템 내비게이션과 분리된 영역을 참고한다. 최신 앱 실측이나 공식 높이 규격으로 간주하지 않는다.
- 선택: 기본 높이 72pt, 위·아래 여백 각각 8pt, 전체 높이에 bottom safe-area inset을 추가한다. 글자 배율 증가분도 높이에 반영한다. 가로 화면에서도 아이콘 아래 라벨을 유지한다.
- Expo Router에 포함된 BottomTabBar 구현에서 사용자 height가 기본 inset 포함 높이를 대체하고 사용자 padding이 기본 padding을 덮어쓰는 것을 확인했다. 높이와 bottom padding 양쪽에 inset을 명시하여 한 번만 확보한다.

## 검증 환경과 한계

- Android·iOS·Web 공통 변경. 새 의존성 없음.
- Chrome 연결, localhost:8090, mock API. 앞선 연결 복구에서 내장 브라우저가 제공되지 않고 Chrome만 발견되어 해당 연결을 이어서 사용했다.
- native 홈 제스처, Android 3버튼 내비게이션, iOS 홈 인디케이터는 실제 기기에서 별도 확인해야 한다. Web 캡처는 native inset 검증을 대신하지 않는다.

## 구현 후 화면 감사

1. [변경 전 오늘 390×844](./01-before-390.png): 64px 하단 바. 비교 기준으로 캡처했다.
2. [변경 후 오늘 390×844](./02-after-390.png): 정상. 새 번들 reload 후 72px 하단 바와 8px 아래 여백을 확인했다. DOM 기준 각 탭은 130×55px, y=781로 최소 44px 터치 높이를 충족한다. 빠른 기록 버튼도 탭 위로 함께 이동했다.
3. [달력 320×844](./03-calendar-320.png): 정상. 탭 클릭으로 달력 이동·선택 상태를 확인했다. 세 라벨이 잘리지 않고 하단 바 안에 표시된다. 본문은 별도 스크롤 영역이다.
4. [더보기 430×844](./04-more-430.png): 정상. 탭 이동·선택 상태와 세 라벨을 확인했다. 긴 본문과 하단 바가 분리되어 있다.

모든 PNG는 이번 실행에서 캡처하고 직접 확인했다. 변경 범위에서 높은 심각도의 Web 시각 문제는 발견하지 않았다. 로딩·오류 데이터 처리에는 변경이 없다. 키보드 표시 중 native 탭 숨김, 화면 회전, 실제 글자 배율 1.5 및 스크린리더는 이번 Web 감사에서 검증하지 않았다.

코드 계산상 bottom inset 0/24/34일 때 전체 높이는 72/96/106, bottom padding은 8/32/42다. 글자 배율 1.5에서는 라벨 증가분 8이 높이에 더해진다. 이 수치는 기기 실측 결과가 아니다.
